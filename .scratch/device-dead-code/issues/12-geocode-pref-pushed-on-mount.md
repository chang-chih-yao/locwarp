# 12 地址搜尋：前端每次掛載都把自己的搜尋來源設定推到後端，另一個 origin 的頁面會蓋掉共用的 `settings.json`

Blocked by: (none)
Type: task
相關：`.scratch/device-dead-code/issues/01-remove-pin-ip-map-and-lockdownd-scan.md` 的 Comments「範圍外、沒修」。01 號票在瀏覽器驗證時發現這件事，只記在已關閉的票裡，沒有開票。2026-11-11 另一個 session 審 device-dead-code 全部的票時指出，照使用者的決定開成這張。

這張不是裝置連線，也不是 dead code。放在 `device-dead-code` 是因為它是從 01 號票帶出來的。

## 為什麼

`AddressSearch` 每次掛載，都會把這個頁面 localStorage 裡的搜尋來源設定推到後端，後端寫進 `~/.locwarp/settings.json`。這個檔案是 dev 後端和安裝版共用的。

localStorage 是照 origin 分開存的。在另一個 origin 開 LocWarp 的頁面（例如瀏覽器驗證用的 5174），那邊的 localStorage 是空的，推出去的就是預設值：來源 `arcgis`、ArcGIS key 是空字串。結果是存在後端的來源被改成 `arcgis`，ArcGIS key 被清掉。

後端存的這份設定只有手機網頁控制的地址搜尋在用。所以實際的影響是：手機網頁的地址搜尋會暫時改用沒有 key 的 `arcgis`，直到原本的頁面再掛載一次、把自己的設定推回去。

下面的行號都是 `9753c48` 時的位置，開票時逐一對過。動手前以內容為準，先用 grep 再對一次。

## 現況

- 前端 `frontend/src/components/AddressSearch.tsx`：
  - `:31-47`：`provider`、`googleKey`、`arcgisKey` 的初始值從 localStorage 讀（`locwarp.geocode_provider`、`locwarp.google_geocode_key`、`locwarp.arcgis_geocode_key`）。讀不到時是 `arcgis` 和兩個空字串。
  - `:59-63`：`syncToBackend` 呼叫 `setGeocodeProviderPref`。來源不是 `google` 時，Google key 一律送空字串。
  - `:114-120`：掛載時的 `useEffect` 呼叫 `syncToBackend(provider, googleKey, arcgisKey)`。註解寫的理由是：使用者可能在有這個同步之前就選了 Google 或 Photon，或是後端的 `settings.json` 被重設過。
  - 用到 `AddressSearch` 的只有 `frontend/src/components/ControlPanel.tsx:1014`。
- `frontend/src/services/api.ts:292-293`：`setGeocodeProviderPref` 送 `PUT /api/geocode/provider-pref`，內容是 `{ provider, google_key, arcgis_key }`。
- 後端 `backend/api/geocode.py:75-92` 的 `set_provider_pref`：
  - `provider` 直接蓋掉。
  - `google_key` 是空字串時不動，存著的 Google key 會留著。
  - `arcgis_key` 是 `None` 時不動，是空字串時清掉（`:58` 的註解寫了這個規則）。前端一定會送字串，所以空的 localStorage 會清掉 ArcGIS key。
  - 最後呼叫 `app_state.save_settings()`，把整份設定寫回 `~/.locwarp/settings.json`（`backend/config.py:27-29`、`backend/main.py:142-157`）。
- 誰讀後端存的這份設定：
  - `backend/api/phone_control.py:618-642` 的 `phone_geocode`：手機網頁控制的地址搜尋。
  - `backend/api/geocode.py:62-72` 的 `get_provider_pref`。
  - 電腦上的地址搜尋不讀它：`frontend/src/services/api.ts:268-276` 的 `searchAddress` 每次都從 localStorage 讀來源和 key，放進請求裡。
- 所以空 origin 的頁面掛載一次之後：
  - 後端的來源變成 `arcgis`，ArcGIS key 變成空的，Google key 不變。
  - 電腦上的地址搜尋不受影響。
  - 手機網頁的地址搜尋改用沒有 key 的 `arcgis`。
  - 原本的頁面（5173 或安裝版）下次掛載時，會把自己的設定推回去。
- 01 號票的 Comments 記的是實際看到的請求：5174 驗證頁掛載時送了 `PUT /api/geocode/provider-pref`，來源是 `arcgis`，key 是空的。這次只讀了程式碼，沒有重新在瀏覽器跑。
- `~/.locwarp/settings.json` 跟安裝版共用這件事，`docs/pipi-mushroom.md:577-580` 也記了一筆（安裝版會把 `pipi_*` 的欄位洗掉）。那是另一個問題，但原因一樣：兩邊寫同一個檔案。
- 歷史：`e85e3ec`（v0.2.150）加的，讓手機網頁的地址搜尋跟著電腦選的來源走。
- 這幾段都是上游的程式。這裡改了，之後合併上游碰到會衝突。

## 可能的做法

- A. 不改程式，改成 `wontfix`：
  - 影響只到手機網頁的地址搜尋，而且原本的頁面下次掛載就會推回去。
  - 瀏覽器驗證時，攔截所有不是 GET 的請求就不會發生。之前的驗證已經這樣做過。
- B. 不改程式，把「驗證頁要攔掉這個 PUT」寫進文件。要先決定寫在哪裡：現在 repo 裡沒有講瀏覽器驗證做法的文件。
- C. 改前端：localStorage 沒有存過搜尋來源時，掛載時不推。
  - 這樣空 origin 的頁面不會蓋掉後端的設定。
  - 要顧到掛載時推送原本的目的：後端的 `settings.json` 被重設過時，要能從 localStorage 補回去。有存過設定的頁面照樣推，這個目的還在。
  - 改的是上游的元件。
- D. 改成後端存的那份才是準的，前端掛載時改成讀後端。這是改設計，範圍大很多。
