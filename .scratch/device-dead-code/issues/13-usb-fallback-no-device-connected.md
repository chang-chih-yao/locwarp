## 為什麼

手機用 WiFi 通道連著、同時也插著 USB 時，按「停止通道」，後端會改用 USB 連回去。照程式碼，這條路成功時沒有通知前端，畫面可能停在「已中斷」，但後端其實已經用 USB 連上。

下面的行號都是 `23dd3bb` 時的位置。動手前以內容為準，先用 grep 再對一次。

## 現況

- 後端 `backend/api/device.py` 的 `wifi_tunnel_stop`（`:1294`）：
  1. `_cleanup_wifi_connection_for`（`:1334`）中斷 WiFi 連線，廣播 `device_disconnected`（`:582`），原因是 `wifi_tunnel_stopped`，帶 `remaining_count`。
  2. USB fallback（`:1337-1385`）：那台如果在 USB 清單裡，就 `dm.connect`、重建 simulation engine（`:1353-1361`）。成功時只記一行 log（`Switched back to USB connection`），沒有廣播 `device_connected`。
  3. 回傳 `{"status": "stopped", "udids": [...]}`。
- 其他連上裝置的路都有廣播 `device_connected`：`:43`、`:747`、`:1645`，和 usbmux watchdog 的 `backend/main.py:595`。
- 前端：
  - `frontend/src/hooks/useDevice.ts:484-495` 的 `stopTunnel`：呼叫完只把那個通道從 `tunnels` 拿掉，不重抓裝置清單。
  - 收到 `device_disconnected` 時（`:89-123`）：把那台標成沒連線，然後呼叫一次 `listDevices()`。
  - 這次 `listDevices()` 是在廣播之後馬上發的，那時 USB fallback 還沒連上的話，拿到的就是沒連線。之後沒有別的事件讓前端再抓一次。
  - 前端沒有定時重抓裝置清單。`frontend/src/App.tsx:451` 的 `setInterval` 只查冷卻時間。
  - `frontend/src/hooks/useSimulation.ts:565-585`：`remaining_count` 是 0 時，會顯示「裝置連線中斷…請重新插上 USB」。
- usbmux watchdog 不會補救：它只自動連「插著 USB 但沒連線」的裝置（`backend/main.py:554`）。fallback 成功後這台已經在連線清單裡，watchdog 不會動它，也就不會送 `device_connected`。
- 所以照程式碼推，可能的結果是：
  - 畫面上那台顯示沒連線；它是唯一一台時，還會出現連線中斷的訊息。
  - 後端其實已經用 USB 連上，engine 也建好了。
  - 使用者重新整理頁面，或按一次會重抓清單的按鈕，才會看到已連線。
- 歷史：USB fallback 是 `99bc4b2`（v0.1.13 的 commit，第一個包含它的 tag 是 v0.1.14）加的。usbmux watchdog 的自動連線是 v0.1.42（`95f4de7`）才有的，比它晚。
- 上游 `upstream/main` 一樣：`backend/api/device.py:1501` 成功時也只記 log。

## 沒查證的

- 整件事沒有實際跑過。要查的是：`listDevices()` 的回應和 USB fallback 的 `dm.connect` 誰先完成。fallback 夠快的話，畫面可能本來就是對的。
- 什麼情況下手機會同時有 WiFi 通道和 USB：
  - 照 `backend/main.py:554`，手機已經用 WiFi 連著時再插上 USB，watchdog 不會另外用 USB 連它。所以「WiFi 連著、USB 也插著」是會發生的，例如連著的時候拿去充電。這也是讀程式碼推的。
- fallback 和 watchdog 會不會同時去連同一台：WiFi 連線清掉之後，到 fallback 的 `dm.connect` 完成之前，這台在 watchdog 眼中是「插著 USB 但沒連線」。沒有查這段時間 watchdog 剛好跑到會怎樣。

## 可能的做法

- A. fallback 成功時補上 `device_connected` 的廣播，內容照其他幾處（`udid`、`name`、`ios_version`、`connection_type: "USB"`）。
- B. 拿掉 `wifi_tunnel_stop` 的 USB fallback，交給 usbmux watchdog：它本來就會在 2 秒內把插著 USB 的裝置連回來，而且會廣播。
  - 這是改行為：停通道後會先看到已中斷，再看到重新連上。
  - 10 號票拿掉的 `device_error` 就在這段 fallback 的失敗處理裡。
- C. 前端 `stopTunnel` 呼叫完之後重抓一次裝置清單。這時 fallback 已經做完，清單是對的。但 `useSimulation` 的連線中斷訊息不會因此消掉。
- D. 查證後發現實際上不會發生，改成 `wontfix`。
