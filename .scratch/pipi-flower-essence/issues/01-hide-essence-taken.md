# 01 原站標過拿過精華的花，在 LocWarp 會被藏起來

Status: ready-for-agent
Blocked by: (none)
Spec: `.scratch/pipi-flower-essence/spec.md`

## 做什麼

這張票做唯讀的那一段，從後端一路做到畫面。

玩家在手機或原站上把一朵花標成**拿過精華**（GLOSSARY），回到 LocWarp 打開蘑菇地圖圖層時，那朵花不會出現在地圖上。標記到那朵花的枯萎時間就失效；花重新開花後，會再出現。

打開圖層時，標記清單還沒讀到之前花先不畫，蘑菇、煙霧照常畫，拿過的花不會先閃出來再消失。讀不到標記清單時，所有花照常顯示，面板狀態列多一行「精華標記讀取失敗」。

這張票還沒有任何可以改變標記的介面：沒有勾選框、沒有按鈕、沒有 ✓。拿過精華的花一律藏起來，等於「顯示拿過精華的花」固定是初始值（不勾）。

## 驗收條件

- [ ] **先實測原站格式。** 這一步要先做，結果會影響後面所有工作。
  - 請使用者先在原站或手機上標一朵花，確保清單不是空的。
  - 用 `start.py` 把 LocWarp 跑起來，透過後端自己的 client 打 `GET /api/pipi/essence`。
  - 為了看到原始格式，可以暫時把原始回覆的欄位名稱、型別和筆數記到 log。看完就拿掉，不要 commit。cookie 照規則不得出現在任何輸出裡。
  - **交叉比對**：拿使用者標過的那朵花，確認清單裡的 `(mapObjectId, bloomedTimeMs)` 跟 items API 的 `(id, bloomedMs)` 對得上，算出來是同一個識別。對不上的話停下來回報，整個功能都靠這一點。
  - 把結果寫進本票的 Comments：
    - 清單的欄位名稱、id 是數字還是字串、時間欄位的型別、有沒有 `nowMs` 之類的額外欄位。
    - items 裡 id 和盛開時間的實際型別。id 是數字的話，前端 `PipiItem.id` 的型別宣告跟實際不符，記下來回報，不在這張票改。盛開時間有小數的話，照 spec「送出的值」回頭改 spec，`PUT` 和「能不能標記」一起放寬。
    - 交叉比對的結果。
  - 格式跟 spec「原站協定」不一樣時，先改 spec，再往下做。
- [ ] 後端可以讀標記清單：client 新增讀清單的方法，加上 `GET /api/pipi/essence`。
  - 回覆的形狀和正規化規則照 spec「後端」。
  - 不快取，跟 items 走同一條排隊和間隔路徑，錯誤碼也照 items 轉。
- [ ] 切面 A 的讀取部分有測試：payload、正規化、不快取、讀清單的錯誤照原樣往外拋。
- [ ] 新增拿過精華純模組，包含標記的識別、標記狀態（含「還沒讀到」）、用清單回覆整份取代、算不算拿過精華（拿過、沒拿過、還不知道）。
  - 清單內容跟舊狀態一樣時，回傳原本那個狀態物件。
  - 切面 B 除了「設定回覆」以外，其他測試都要有，包含「還沒讀到」和「回傳原本的狀態物件」。
- [ ] 花的子篩選設定多一欄 `showEssenceTaken`，初始值是 false。
  - resolver 要相容這個功能之前存的兩欄格式。
  - 花的子篩選的判斷多收「是不是拿過精華」這個參數，有拿過、沒拿過、還不知道三種。沒勾第三條時，拿過和還不知道的花都不顯示；蘑菇、煙霧一律通過。
  - 切面 C 的「花的子篩選第三條」和「初始值」測試都要有，包含三個子選項八種組合、每種組合三種狀態的真值表。
- [ ] 抓取 planner 回答「現在要不要讀標記清單」，並能記下「這一輪讀過了」。切面 E 的測試全部要有。
- [ ] 圖層照 spec「讀標記清單的時機」和「圖層」接起來：
  - 每一輪只在第一個不是 hide 的決定時讀一次清單，而且只在 `configured` 是 true 的那一輪讀。
  - 抓取迴圈停下來時不送、也不記成讀過。
  - 清單收到 429 時不記成讀過，迴圈的退避時間照 `retry_after` 設定；退避期間不送，退避結束後下一個不是 hide 的決定再讀。畫面照讀取失敗處理。
  - 429 以外的讀取失敗算讀過。
  - 標記狀態改變時只重建 marker，不重抓 items。
  - 被藏起來的花不佔點位上限。
  - 標記狀態的生命週期：
    - 還沒讀到時花先不畫，蘑菇、煙霧照常畫；靠花的子篩選的「還不知道」來做，不在圖層另外寫判斷。
    - 圖層關閉、cookie 被清掉時，回到還沒讀到。
    - cookie 重新設定（`updated_at` 改變）、按「重新整理」開始新的一輪時，舊的標記先留著，等新清單回來再取代。原站用 Set-Cookie 續期不算，不會開新的一輪。
    - 讀取失敗（包括 429）時，清空成「讀到了、一朵都沒有」，所有花照常顯示，面板顯示「精華標記讀取失敗」（英文 `Couldn't load essence marks`）。這一行留到下一次讀取成功，或下一輪開始。
  - 標記的過期用伺服器時間判斷。
- [ ] 人工驗證，逐項回報：
  - 在原站標過的花，在 LocWarp 不會出現。
  - 狀態列筆數等於實際的 marker 數。
  - spec「人工驗證 → Network 請求數」裡跟讀取有關的各項：
    - 打開圖層、按重新整理、cookie 重新設定各一次。
    - 圖層開著時重新整理整個頁面，只有一次。
    - 60 秒刷新、平移、縮放都沒有。
    - zoom 15 以下打開不讀，縮放到 15 才讀。
  - spec「人工驗證 → 還沒讀到時先不畫花」兩項：用 fetch 攔截延遲清單回覆，打開圖層和按重新整理時，拿過的花都沒有閃出來。
  - 用 fetch 攔截讓清單請求失敗：所有花都顯示，面板出現提示。
  - 用 fetch 攔截讓清單請求回 429：所有花都顯示、面板出現提示，退避結束後又送出一次清單請求。
- [ ] 文件：
  - 蘑菇地圖設計文件：Pieces 表加上新模組；Site protocol 補上標記端點、讀清單的實測格式和交叉比對的結果；Throttling 補上讀清單請求，包括只在確定有 cookie 的那一輪讀、429 等退避結束再補讀。
  - 蘑菇地圖 rules 檔：`paths` 和 Tests 那一行加上新模組、新測試。
- [ ] 回歸：`tests/frontend/*.ts`、`tests/pipi/` 全部照跑，`npm run build` 要通過。逐條回報 mutation check 的結果，有任何 skipped 都要說明。
