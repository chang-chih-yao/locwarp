# 03 在花的 popup 手動標記拿過精華、也能取消

Status: ready-for-agent
Blocked by: 02
Spec: `.scratch/pipi-flower-essence/spec.md`

## 做什麼

已盛開、還沒枯萎的花，popup 裡會出現「我拿過精華了」按鈕，放在「瞬移+撈水果」右邊，兩顆一樣寬。

- **按下之後**：等原站確認成功。沒勾「顯示拿過精華的花」時，popup 關掉、花消失；有勾時，popup 留著，按鈕變成「已拿過精華（取消）」，花加上 ✓。
- **取消**：再按一次就取消標記。
- **跟原站同步**：標記寫進原站帳號，手機上的原站也看得到。

## 驗收條件

- [ ] 後端可以設定標記：client 新增設定標記的方法，加上 `PUT /api/pipi/essence`。
  - body 和回覆的形狀照 spec「後端」。id 原樣轉給原站，保留數字或字串的型別。
  - body 用 pydantic 嚴格驗證：字串或整數的 id 有長度上限，盛開時間是正整數，`collected` 是布林值。
  - 不快取，跟 items 走同一條排隊和間隔路徑。
  - 切面 A 的「設定」「不快取」「API body 驗證」測試要有，「錯誤」也要測設定這個方法：`PipiError` 照原樣往外拋。API 測試用暫時的 `SETTINGS_FILE`。
- [ ] 拿過精華模組能用設定回覆更新標記狀態：
  - 標記時用回覆的失效時間；回覆是 0 時，改用那朵花的 `wiltingMs`。
  - 取消時刪掉這個識別。
  - 不改動舊的狀態物件。
  - 套在「還沒讀到」的狀態上，結果仍然是還沒讀到。
  - 切面 B 的「設定回覆」測試要有。
- [ ] 花的規則模組新增「能不能標記拿過精華」（Q4），切面 C 的「能不能標記」測試全部要有。其中要有測試鎖住：
  - 跟撈水果的差別：盛開 61 分鐘、彩帶期過了的花能標記、不能撈水果。
    - 撈水果在 pipi-fruit-approach 02 號票之後只對彩帶花，本身就要求有枯萎時間，所以「沒有枯萎時間」已經不是兩者的差別。
    - 「沒有枯萎時間不能標記」的測試還是要有，它鎖的是標記自己的條件。
  - 盛開時間有小數就不能標記，跟 `PUT` 只收正整數一致。
- [ ] popup 的動作照 spec「圖層 → popup 的按鈕列」改：
  - 每個動作都改成收到整筆點位，不再只收座標；瞬移、導航、撈水果從裡面取座標，行為不變。04 號票的撈水果直接沿用這一點。
  - MapView 現在把收座標的 `onTeleport`、`onNavigate`、`onPipiCollectFruit` 直接傳給圖層（MapView 呼叫 `usePipiMushroomLayer` 的地方）。三個都要在 MapView 包一層、從整筆點位取座標，build 才會過。撈水果把整筆花一路傳到 App 是 04 號票的事，這張票不改 App 的撈水果。
  - 改 `onCollectFruit` 的型別時，順便修正 `usePipiMushroomLayer.ts` 裡它過時的註解：現在寫「不是花苞、還沒枯萎的花才有」，pipi-fruit-approach 02 號票之後只有彩帶花才有。
  - 共用的點擊處理不再先關 popup，改由各個動作決定：瞬移、導航、撈水果照舊先關；標記不關。
  - 標記按鈕要有自己的動作對應。
- [ ] popup 的按鈕列：
  - 兩顆按鈕在同一列、等寬，撈水果在左；只出現一顆時佔滿整列；兩顆都沒有時，整列不出現。
  - 撈水果只對彩帶花，所以兩顆並排只出現在彩帶花上，大部分盛開的花只有標記按鈕，佔滿整列。
  - 按鈕文字在打開 popup 時，依當下是不是拿過精華來決定；還不知道時用「我拿過精華了」。
  - 在中文、英文介面下實際看過。會換行時，只把同時出現兩顆按鈕的 popup 加寬，其他 popup 寬度不變，按鈕文字也不改。
  - 加寬的做法照 spec：Leaflet 的 `minWidth`、`maxWidth` 在建立 marker 時就固定，現在的 `maxWidth` 280 會把內容夾住。同時有兩顆按鈕時，popup 內容加 class 撐開最小寬度，花的 marker 的 `maxWidth` 放寬到容納得下。
- [ ] 圖層提供一個標記動作，手動按鈕和 04 號票的自動標記共用它，行為照 spec「標記動作」：
  - **只做四件事**：送出請求、管「存檔中」清單、用回覆更新標記狀態、回傳結果。結果分成三種：成功、失敗（帶原因）、存檔中所以忽略。
  - **不關 popup、不跳提示**：這兩件交給呼叫端。共用動作如果關 popup，自動標記成功時會把使用者當下開著的別朵花或書籤的 popup 關掉，圖層關著時也一樣；兩邊都跳提示的話，後一個會蓋掉前一個。
  - **防重複送出**：標記動作自己記一份「存檔中」的識別清單，放在 ref、不放進 React state。同一朵花還在存檔中就直接忽略，不送第二次，回傳「存檔中所以忽略」。失敗時從清單拿掉也是它的事。
  - 圖層關著時也能用，04 號票需要這一點。
- [ ] 手動按鈕是標記動作的呼叫端，自己負責 popup 和提示：
  - **存檔期間按鈕停用**：點下時直接把按鈕設成停用；popup 每次打開，包括整層重建後重開，都讀「存檔中」清單，把存檔中的花的按鈕畫成停用。
  - **接受 popup 關掉再重開**：標記成功會整層重建，有勾「顯示拿過精華的花」時 popup 靠既有的機制重開，內容照新的標記狀態重畫。不另外做就地更新。
  - **成功後**：
    - 沒勾時，開著的 popup 正是這朵花才關掉。存檔期間使用者可能已經改開別朵花或書籤的 popup，那個不關。
    - 有勾時 popup 留著。
    - 提示「已標記為拿過精華」或「已取消拿過精華標記」。
  - **失敗時**：提示「標記拿過精華失敗：{error}」或「取消拿過精華標記失敗：{error}」；popup 還開著的話按鈕恢復可按。popup 不關，標記狀態不變；不自動重試，也不停掉抓取迴圈。
  - **存檔中所以忽略**：存檔期間按鈕是停用的，正常收不到；收到時不跳提示。
  - **接受的邊界**（2026-11-09 使用者確認）：勾著「顯示拿過精華的花」、標記狀態還沒讀到時標記成功，狀態仍然是還沒讀到，不會整層重建。開著的 popup 按鈕會一直停用，等清單回來、整層重建才恢復。只會發生在打開圖層後、清單回來前那 1～2 秒，不另外處理。
  - **提示的接線**：顯示 toast 的函式由 App 經 MapView 傳進圖層。
  - 中英文字串照 spec 的介面文字表，包括最後補的標記失敗、取消失敗兩行。
- [ ] 實測原站，使用者已經同意（Q12）：
  - 動手前先告訴使用者要標哪一朵花。
  - 在 LocWarp 標記一次，到原站或手機上確認出現了；再取消，確認消失了。
  - 取消之後讀一次清單，看那一筆是被拿掉，還是留著並帶 `collected: false`（01 號票實測時每一筆都帶 `collected: true`，原站和 LocWarp 讀清單時都不看這個欄位）。
    - 如果留著，**停下來**回報使用者，由使用者決定怎麼處理，這張票先不標 resolved（2026-11-09 使用者確認）。
    - 原因：LocWarp 讀清單時不看 `collected`，留著的話，取消過的花下一次重讀（按重新整理、重開圖層）就會又被當成拿過，取消功能（user story 13、14）等於失效。
  - 量一筆標記都沒有時清單的格式：原站回 `items: []`，還是沒有 `items` 或是 null。後端只把 `items: []` 當成一筆都沒有，其他都報 `pipi_unavailable`，面板會一直顯示「精華標記讀取失敗」。
    - 先用最省事的量法：使用者唯一的那筆標記（01 號票實測的黃色萬壽菊）在台北時間 2026-11-10 18:06:44 失效。做這張票時已經過了這個時間的話，先開一次圖層、讀一次清單，只送讀取請求，不用動任何標記。
      - 原站會清掉失效的標記的話，清單就自然變空，這樣就量到了。
      - 清單回 `pipi_unavailable`（面板顯示「精華標記讀取失敗」）的話，就是格式不是 `items: []`，照下面最後一項處理。先確認不是網路或登入的錯誤。
      - 清單裡還留著那筆失效的標記，就是原站連失效的標記也留著，改用下面的量法。
    - 標記之前先讀一次清單。如果已經是空的，這一次就量到了，取消之後再讀一次確認。
    - 清單裡還有別的標記時（原站可能連失效的標記也留著），先回報使用者，由使用者決定要不要先在原站取消那些標記；取消之後，再取消本次的標記並讀一次清單。
    - 量不到的話，在本票的 Comments 記下「空清單格式沒量到」和原因，spec「還沒驗證」那一項留著。
    - 量到的不是 `items: []` 時，回報使用者，先改 spec 再改後端。
  - 把設定回覆的實際格式寫進本票的 Comments。跟 spec 不一樣時，先改 spec 再繼續。
- [ ] 人工驗證，逐項回報：
  - **哪些請求可以打到原站**，照 spec「人工驗證」的規則：
    - 設定請求只有上面「實測原站」的那一次標記和一次取消放行。
    - 其他的設定請求一律由攔截器回假的 `{wiltingMs}`。連點、延遲加重新整理、成功後花消失、有勾時出現 ✓ 和取消按鈕，這些需要「標記成功」的項目都用假的成功。
    - 用攔截器改 items 的 `bloomedMs` 造彩帶花時，設定請求絕對不能放行，否則假的盛開時間會寫進使用者的原站帳號。
    - 瞬移、導航比照 01 號票在瀏覽器攔下，只記下送出的內容。
  - 兩顆並排和加寬：彩帶花很少（pipi-fruit-approach 02 號票實測新竹 344 個 popup，只有 1 朵），事先計畫用攔截器改 items 的 `bloomedMs` 造一朵。
  - spec「人工驗證」裡 popup、標記與取消的各項，包括「存檔中」：用 fetch 攔截延遲設定請求，連點只送出一次；延遲期間按「重新整理」讓整層重建，popup 重開時按鈕還是停用。
  - 存檔期間改開別朵花的 popup：沒勾時標記成功，別朵花的 popup 不會被關掉。
  - 用 fetch 攔截讓標記請求失敗：出現「標記拿過精華失敗：…」、按鈕恢復、花沒有被藏。取消請求失敗時出現「取消拿過精華標記失敗：…」。
  - 自己按標記之後，沒有新的標記清單請求。
  - 瞬移、導航、撈水果三顆按鈕照舊會關掉 popup，而且走到的座標沒變。
