# 04 撈水果直線走到花上之後，自動標記拿過精華

Status: resolved
Blocked by: 03
Spec: `.scratch/pipi-flower-essence/spec.md`

## 做什麼

按下「瞬移+撈水果」，所有裝置都直線走到花上之後，LocWarp 自動替這朵花標記**拿過精華**，不用再打開 popup 按一次。

以下情況不標記，花留在地圖上讓玩家重來：

- 中途按了停止。
- 走到一半改去別的地方。
- 裝置斷線。
- 群組模式下有任何一台沒走到。

中途暫停再繼續，走到花上時一樣會標記。

## 驗收條件

- [x] 撈水果把完整的那筆花帶到 App，不再只帶座標。popup 的動作在 03 號票已經改成收整筆點位，這張票把它一路傳過去。03 號票在 MapView 包了一層、只把座標傳給 App，這張票把那一層改成整筆傳過去。自動標記用的是按下那一刻的這筆花。
- [x] 撈水果模組新增抵達監看，是一個純函式，規則照 spec「自動標記」：
  - 每台裝置先等「開始走、終點是這朵花」的事件；開始之後，只有 `navigating`、`paused` 算還在走，暫停再繼續不算取消。
  - 終點相同的 `navigation_complete` 算抵達。
  - 開始之後、抵達之前，下面這些都算取消：
    - `state_change` 變成 `navigating`、`paused` 以外的任何狀態：idle、斷線，以及 teleporting、joystick、looping、`reconnecting` 等。後端換模式之前會先 `stop()` 送 idle，所以現在 idle 和斷線以外的狀態不會直接出現；用白名單是為了以後新增的狀態。
    - 對到這台裝置的 `device_disconnected`。
    - 終點不同的 `navigation_complete`。
  - `device_disconnected` 有兩種形狀：USB 拔掉、裝置掉線時只帶 `udids`；WiFi 通道停掉、使用者斷線時 `udid` 和 `udids` 都帶。`udids` 是陣列就用它，不是才用 `udid`；結果是空的（`udids` 是空陣列，或兩個都沒有）就當成所有裝置都斷線，跟 `useDevice.ts` 一致。後端目前不會送出空陣列。
  - 群組模式要每台裝置都抵達；任何一台取消，整個就取消。
  - 不在清單裡的裝置送來的事件一律忽略。
  - 15 秒的開始期限，從建立監看（送出導航前一刻，見「接線」）算起。
    - 每餵一筆事件，先檢查期限、再處理事件：15 秒後才到的開始事件判成取消，不當成開始。
    - 原因：監看只在收到事件時往下判斷。少了這個順序，一個一直沒收到開始事件的監看，之後用「導航到這裡」走到同一朵花就會誤標，這正是設這個期限要防的情況。
  - 終點的座標差在 1e-6 度以內算相等。
  - 抵達和取消都是最終結果，之後再餵事件也不會改變。
  - 切面 D 的測試全部要有，包括 `device_disconnected` 的各種形狀（含 `udids` 空陣列）、走路中收到白名單以外的狀態、15 秒後才收到開始事件。
- [x] 接線：
  - 監看在 `runFruitApproach` 的導航 callback 裡、送出導航**前一刻**才建立；群組模式在 150 ms 的等待之後。
    - 不能等導航 API 回覆之後才建立，因為開始走的事件可能比回覆更早到。
    - 也不在瞬移之前建立，否則 15 秒的期限會把瞬移和等待的時間算進去。
    - 瞬移失敗、撈水果中止時不會呼叫導航 callback，所以根本不會建立監看。
  - 導航沒有開始，或群組模式有任何一台導航沒送成功，就丟掉監看。
  - 監看有了最終結果（全部抵達或已取消）之後就丟掉。
  - WS 一斷線就丟掉所有監看，不等重連。理由照 spec「自動標記 → 接線」：斷線期間漏掉 `navigation_complete` 的話，監看會一直停在走路中，之後用「導航到這裡」走到同一朵花就會誤標。
  - 監看只存在前端的記憶體裡。
- [x] App 叫圖層標記的介面：MapView 建好地圖時交給 App 的既有地圖介面，多提供一個「自動標記這朵花」的函式。下面全部抵達時的檢查、呼叫標記動作、跳提示，都在這個函式裡做完；App 只在全部抵達時呼叫它，不另外拿標記狀態和時間偏移。
  - **透過 ref 讀當下的狀態**：MapView 只在建立地圖的 effect 裡呼叫一次 `onMapReady`，交出去的函式不會再換。所以這個函式要透過 ref 讀圖層當下的標記狀態、時間偏移和 toast 函式，不能閉包建立地圖那一刻的值。
  - 閉包舊值的話，標記狀態會一直是那一刻的「還沒讀到」，照「還不知道當成還沒拿過」每次都送，不會報錯。這段接線沒有自動化測試，靠下面人工驗證的 user story 27 那一項。
- [x] 全部抵達時，用當下的伺服器時間檢查兩件事：花的規則模組說「能標記」，而且拿過精華模組沒有說「拿過」。
  - 兩者都成立，才呼叫 03 號票的標記動作；否則直接跳過，不跳提示。
  - 「還不知道」當成還沒拿過，照樣標記。圖層在途中被關掉時，標記狀態會回到還沒讀到，這時還是要標。
  - 伺服器時間用圖層最近一次的偏移；圖層沒有資料時，用本機時鐘。
  - 成功時提示「已自動標記為拿過精華」；失敗時提示「自動標記拿過精華失敗：{error}」，英文照 spec 的介面文字表。不重試。沒有 cookie 也算失敗，照樣提示。
  - 標記動作回「存檔中所以忽略」時（例如走路途中自己按了、還在存檔），不跳提示，也不當成失敗（user story 27）。
  - 不關 popup。03 號票的標記動作不關，這裡也不關，使用者當下開著的 popup 不受影響。
  - 圖層在途中被關掉，走完照樣標記。
- [x] 撈水果既有的行為不變：
  - 起點、直線走、瞬移失敗就中止、群組模式等 150 ms、最近地點、送出時的提示都照舊。
  - 既有的撈水果測試要全部照綠。
- [x] 人工驗證，逐項回報：
  - 前提：要接上實機，找到還在彩帶期內的花，撈水果按鈕只對彩帶花出現。比照 03 號票，動手前先告訴使用者要撈哪一朵：撈水果會移動實機的位置，自動標記會寫進原站帳號。
  - 哪些請求可以打到原站，照 spec「人工驗證」的規則：設定請求只有下一項那次放行，其他走完會自動標記的項目都由攔截器回假的結果，看送出的內容就好。
  - 單機實際撈水果一次，走完會自動標記，原站或手機上看得到；看完要不要取消，由使用者決定。
  - user story 27：走路途中自己打開 popup 按了標記（攔截器回假的成功），抵達時不再送設定請求，也不跳提示。這一項驗的是「自動標記這朵花」透過 ref 讀到當下的狀態。
  - 撈水果中途按停止，不會標記。
  - 途中關掉蘑菇地圖圖層，走完照樣標記。
  - 有兩台裝置時驗證群組模式；沒有的話，明確回報「跳過」。
- [x] 文件：蘑菇地圖設計文件的撈水果一節，和「拿過精華」一節，都補上自動標記：觸發條件、不標記的情況、群組規則、重新整理頁面就不補標。
- [x] 回歸：`tests/frontend/*.ts`、`tests/pipi/` 全部照跑，`npm run build` 要通過。逐條回報 mutation check 的結果，有任何 skipped 都要說明。
