# 蘑菇地圖：花的「拿過精華」標記

Status: ready-for-agent

## Problem Statement

玩家在蘑菇地圖圖層上找花來採精華、撈水果。每朵花每次開花，精華和水果各只能拿一次；拿完之後要等它枯萎、變回花苞、重新開花，才能再拿。

但 LocWarp 地圖上沒有任何方法記下「這朵花我拿完了」，拿過的花會一直留著：

- 地圖上的花很多（台北市區一個 zoom 15 的畫面就有幾百朵），拿過的跟沒拿過的混在一起，會白跑一趟。
- 原站 pipimushroom.com 有「我拿過精華了」按鈕，標記存在原站帳號裡，手機上的原站也看得到。可是 LocWarp 讀不到這份標記，玩家在手機上標過的花，在 LocWarp 照樣顯示。
- 用「瞬移+撈水果」走到花上之後，玩家還得自己記住這朵已經撈過了。

## Solution

在花的 popup 裡加一顆「我拿過精華了」按鈕，標記跟原站同步，讀寫的是同一份。

- **按鈕位置**：放在「瞬移+撈水果」右邊，兩顆等寬。只有一朵已盛開、還沒枯萎的花才有這顆按鈕。
- **按下之後**：等原站確認成功，那朵花就從地圖上消失。同一朵花重新開花後會再出現。
- **顯示與取消**：面板的花的子篩選多一個「顯示拿過精華的花」，初始值不勾。勾起來後，拿過精華的花會顯示出來，角落加一個 ✓。這時 popup 裡的按鈕變成「已拿過精華（取消）」，再按一次就取消標記。
- **自動標記**：用「瞬移+撈水果」直線走到花上之後，LocWarp 會自動標記拿過精華。中途停止、被打斷或裝置斷線，就不標。群組模式要所有裝置都走到才標。
- **讀取時機**：打開圖層、cookie 重新設定（擴充套件推送或手動貼上）、按「重新整理」時，從原站重新讀一次標記清單。所以在手機上標過的花，回到 LocWarp 也會被藏起來。清單還沒讀到之前，花先不畫，拿過的花才不會先閃出來再消失。

名詞照 GLOSSARY：精華、採精華、水果、撈水果、拿過精華、花的子篩選，都已經寫進 GLOSSARY 的蘑菇地圖段落。

## User Stories

1. 身為玩家，我想在採完一朵花後按「我拿過精華了」讓它從地圖消失，這樣不會再跑去同一朵。
2. 身為玩家，我希望在手機上的原站標過的花，在 LocWarp 也被藏起來，這樣不用兩邊各標一次。
3. 身為玩家，我希望在 LocWarp 標的花，手機上的原站也看得到，因為兩邊是同一個帳號。
4. 身為玩家，我希望標記只對這一次開花有效。同一個花點枯萎、重新開花之後，要再出現在地圖上，因為那時又能拿精華和水果了。
5. 身為玩家，我希望標記到那朵花的枯萎時間就自動失效，不用自己清。
6. 身為玩家，我希望只有已盛開、還沒枯萎的花才有這顆按鈕；花苞、蘑菇、煙霧都沒有，因為只有盛開的花能採精華。
7. 身為玩家，我希望這顆按鈕放在「瞬移+撈水果」右邊、兩顆一樣寬，這樣花的兩個動作排在一起。
8. 身為玩家，我希望一朵花只有其中一顆按鈕時，那顆按鈕佔滿整列。
9. 身為玩家，我希望兩顆按鈕並排時文字不換行。需要的話，popup 可以變寬，但其他 popup 的寬度不要跟著變。
10. 身為玩家，我希望按下後要等原站確認成功才算數；存檔期間按鈕停用，連點也不會送出兩次。
11. 身為玩家，我希望標記成功後 popup 關掉、那朵花立刻從地圖消失，並看到「已標記為拿過精華」的提示。
12. 身為玩家，我想勾「顯示拿過精華的花」，看到我拿過的花，而且每朵角落都有 ✓，一眼就分得出來。
13. 身為玩家，我想在勾著「顯示拿過精華的花」時，打開一朵拿過的花，按「已拿過精華（取消）」把標記取消，以防我按錯。
14. 身為玩家，我希望取消成功後 ✓ 消失、按鈕變回「我拿過精華了」，並看到「已取消拿過精華標記」的提示。
15. 身為玩家，我希望「顯示拿過精華的花」一開始是不勾的，因為我要的就是拿過的花不再出現。
16. 身為玩家，我希望重開 LocWarp 之後，「顯示拿過精華的花」維持我上次的選擇。
17. 身為玩家，我希望存下來的設定是這個功能之前的舊格式時，原本兩個子選項保留我的選擇，第三個用初始值。
18. 身為玩家，我希望「花」關掉時，「顯示拿過精華的花」跟另外兩個子選項一樣變灰，並保留勾選值。
19. 身為玩家，我希望拿過精華的彩帶花在「只顯示彩帶」底下也被藏起來，因為我已經拿完它了。
20. 身為玩家，我希望被藏起來的拿過精華的花不佔點位上限，這樣其他還沒拿的花能畫出更多。
21. 身為玩家，我希望面板狀態列顯示的筆數，是藏掉拿過精華的花之後實際畫出來的數量。
22. 身為玩家，我希望用「瞬移+撈水果」直線走到花上之後，LocWarp 自動替這朵花標記拿過精華，這樣不用再打開 popup 按一次。
23. 身為玩家，我希望撈水果中途按了停止、改去別的地方、或裝置斷線時，不要自動標記，花留在地圖上讓我重來。
24. 身為玩家，我希望撈水果中途暫停再繼續，走到花上時一樣自動標記。
25. 身為群組模式的玩家，我希望所有裝置都走到花上才自動標記，只要有一台沒走到就不標，因為每台裝置是不同的遊戲帳號。
26. 身為群組模式的玩家，我能接受標記只有一份、屬於 pipimushroom 帳號，不分裝置。
27. 身為玩家，我希望走到花上時，如果這朵花已經標記過（例如我走路途中自己按了），LocWarp 不再送一次，也不跳提示。
28. 身為玩家，我希望走到花上時，如果這朵花已經不能標（例如剛好枯萎了），LocWarp 直接跳過，不跳提示。
29. 身為玩家，我希望自動標記成功時看到「已自動標記為拿過精華」；失敗時看到失敗的原因。失敗了不自動重試，我可以自己打開 popup 按。
30. 身為玩家，我希望撈水果途中關掉蘑菇地圖圖層，走完照樣自動標記，因為標記存在原站，跟圖層開不開無關。
31. 身為玩家，我能接受撈水果途中重新整理頁面或關掉 LocWarp 的話，這次就不會補標。
32. 身為玩家，我希望標記失敗時（網路斷了、登入過期、原站限流）看到錯誤提示，按鈕維持原本的狀態、popup 不關、花也不藏，這樣我知道沒成功，可以再按一次。
33. 身為玩家，我希望標記清單讀不到時，地圖照常顯示所有的花，面板狀態列多一行「精華標記讀取失敗」，這樣我知道拿過的花為什麼又出現了。
34. 身為玩家，我希望打開圖層、cookie 重新設定、按「重新整理」時，LocWarp 重新讀一次標記清單，這樣我在手機上剛標的花會同步過來。
35. 身為玩家，我希望打開圖層時，拿過精華的花不會先閃出來再消失；花比蘑菇晚一點出現沒關係。
36. 身為玩家，我希望在原站限流期間按「重新整理」，限流結束後 LocWarp 會自動補讀標記清單，而不是這一輪都讀不到、拿過的花一直跑出來。
37. 身為原站的使用者，我不希望 LocWarp 因為這個功能常常打原站：60 秒的自動刷新、平移縮放都不讀標記清單，zoom 15 以下不讀，自己按標記後也不重讀，app 啟動時圖層已經開著也只讀一次。
38. 身為英文介面使用者，我想看到英文的按鈕、勾選框和提示文字。
39. 身為玩家，我希望 ✓ 在小、中、大三種標記大小下都看得清楚。
40. 身為維護者，我希望標記的識別、過期和狀態更新集中在一個能單獨測試的模組，原站格式改了只要改一處。
41. 身為維護者，我希望原站標記 API 的實際回應格式在實作時用真實帳號驗證過，並記進文件。

## Implementation Decisions

**原站協定**

這一節來自反推原站的地圖腳本（2026-11-09 下載），實作的第一步要用真實帳號驗證。

- **端點**：原站的「花精華資料」端點是 `Handlers/FlowerEssenceData.ashx`，跟地圖資料用同一套加密封包，也同樣要登入。
- **讀取**：送 `{action: "list"}`，回覆的 `items` 是這個帳號全部的標記，不分地區、不帶範圍。每一筆有 `mapObjectId`、`bloomedTimeMs`、`wiltingTimeMs`。
  - 01 號票實測（2026-11-09）：回覆是 `{ok: true, items: [...]}`，沒有 `nowMs`。`mapObjectId` 是字串（例如 `9c19ee876ae44a5f9a92b68d602cc1ea.16`），兩個時間是整數毫秒。
  - 每一筆另外帶 `collected: true`。原站讀清單時不看這個欄位，LocWarp 也不看。
- **設定**：送 `{action: "set", mapObjectId, bloomedTimeMs, collected}`，回覆帶 `mark.wiltingTimeMs`。`collected: false` 就是取消。
  - 03 號票實測（2026-11-10，一次標記、一次取消）：取消的回覆是 `{ok: true, mark: {mapObjectId, bloomedTimeMs, wiltingTimeMs: 0, collected: false}}`。
  - 標記的回覆裡 `mark.wiltingTimeMs` 是那朵花的枯萎時間，這是**推出來的**：標記那一次的原始回覆沒記到，只看到後端回的失效時間等於那朵花的枯萎時間。後端只從 `mark.wiltingTimeMs` 取這個值，沒有就回 0。
  - 取消之後，清單裡那一筆被拿掉，不會留著帶 `collected: false`。
- **送出的值**：`mapObjectId` 和 `bloomedTimeMs` 用 items 回傳的原始值和原始型別，原站自己也是這樣送。
  - 後端把原站 items 的 `id` 原樣轉給前端，所以前端型別宣告的 `id: string` 在執行時不一定成立；id 可能是數字，識別規則和設定標記都照數字、字串兩種處理。
  - 盛開時間：`PUT` 只收正整數，所以「能不能標記」也要求盛開時間是正整數，兩邊一致，按鈕就不會出現在送出去會被 422 擋掉的花上。01 號票實測時記下 items 裡 id 和盛開時間的實際型別；盛開時間有小數的話，兩邊一起放寬。
  - 01 號票實測（2026-11-09，新竹一個 zoom 15 的畫面，62 筆）：items 的 id 全是字串，花的盛開、枯萎時間全是整數，沒有小數，所以不用放寬。
- **標記的識別**：把 id 轉成字串並去掉頭尾空白，加上 `|`，再接上無條件捨去的盛開時間。id 是空的，或盛開時間不是大於 0 的有限數字時，就沒有識別。
- **算不算拿過**：識別要在標記裡，而且失效時間還沒到。失效時間是 0 或沒有值，都不算拿過。
- **原站自己的行為**：開頁時讀一次清單；按下按鈕後，把 `set` 的回覆套進本機的資料，不重讀清單。回覆裡沒有失效時間時，用那朵花的 `wiltingMs`。

**後端**

- **讀標記清單**：蘑菇地圖的 client 新增這個方法。它把回覆正規化成 `{id: 字串, bloomedMs: 整數, wiltingMs: 整數}` 的清單：id 轉成字串、去頭尾空白；id 是空的、或盛開時間不是大於 0 的有限數字，這一筆就丟掉；失效時間沒有值或不合格時，填 0。
  - id 只收字串和整數，布林值和浮點數也丟掉：Python 把 7.0 寫成 `"7.0"`，前端的 `String()` 寫成 `"7"`，永遠對不上。實測 id 全是字串。
  - 回覆裡沒有 `items` 清單（沒有這個欄位、是 null 或不是清單）時報 `pipi_unavailable`，不當成一筆標記都沒有（01 號票 code review 後改，2026-11-09）。原因：items 變空時地圖明顯空掉，標記清單變空卻會靜靜地讓拿過的花全部跑出來，面板也沒有提示。報錯的話，前端照讀取失敗處理，顯示「精華標記讀取失敗」。一筆標記都沒有的帳號原站回什麼還沒實測，見「還沒驗證」。
- **設定標記**：client 新增這個方法。輸入 id（數字或字串，原樣轉給原站）、盛開時間、`collected`，回傳 `{wiltingMs}`，取自回覆的 `mark.wiltingTimeMs`，沒有就填 0。這個值照讀清單時失效時間的規則正規化：小數捨去，不是大於 0 的有限數字（含字串、布林值）就填 0（03 號票 code review 後補，2026-11-10）。
- **節流**：兩個方法都**不快取**，而且都走 items 那條請求路徑：一次只送一個請求、間隔至少 1 秒、遵守 `Retry-After`、登入的 token 過期時重試一次。也就是說，它們跟 items 共用同一套節流。
- **錯誤**：照 items 的方式轉成 HTTP 錯誤碼，前端沿用既有的錯誤文字。429 會帶 `retry_after`。後端的退避時間是整個 client 共用的，不會隨著前端每一輪重設，退避期間任何請求都會馬上被擋回 429，不會打到原站。
- **LocWarp 的 API**：
  - `GET /api/pipi/essence` 回 `{marks: [...]}`。
  - `PUT /api/pipi/essence` 的 body 是 `{id, bloomedMs, collected}`，回 `{wiltingMs}`。
  - body 用 pydantic 限制欄位：id 只接受嚴格的字串或整數，有長度上限；盛開時間是正整數；`collected` 是布林值。
- **不存資料**：LocWarp 不存任何標記，原站才是唯一的來源。
- **不碰 items**：items 的請求、快取、最低 zoom 都不改。

**「拿過精華」純模組（新增）**

- 執行期不 import 任何東西，只用可以直接抹除的 TypeScript 語法，讓 `node --test` 能直接載入。這跟花的規則模組是同一個限制。
- 對外提供：
  - **標記的識別**：給 id 和盛開時間，回傳識別，或者沒有識別。規則見上面的原站協定。
  - **標記狀態**：識別對應到失效時間（伺服器時間的毫秒）。另外有一個「**還沒讀到**」的值，跟「讀到了、但一朵都沒標」分開。沒分開的話，一朵都沒標過的帳號，花會永遠等不到清單而畫不出來。
  - **用清單回覆建立狀態**：整份取代，不跟舊的合併。所以原站已經取消的標記，重讀之後就會消失。
    - 新清單的內容跟舊狀態完全一樣時，回傳原本那個狀態物件。圖層就不會因為內容沒變的清單多重建一次整層，整層重建會關掉再重開 popup。
  - **用設定回覆更新狀態**：
    - 標記時，失效時間取回覆的值；回覆是 0 時，改用那朵花的 `wiltingMs`。
    - 取消時，刪掉這個識別。
    - 回傳新的狀態，不改動舊的。
    - 狀態是「還沒讀到」時，結果仍然是「還沒讀到」。圖層關著時也能標記（自動標記），如果把一筆標記套進「還沒讀到」，之後打開圖層時，這份只有一筆的狀態會被當成讀到了，其他拿過的花就會先閃出來。
  - **算不算拿過精華**：給點位、狀態和伺服器時間，回答「拿過」「沒拿過」或「還不知道」。
    - 有識別、在狀態裡、而且失效時間大於現在，才算拿過（Q2）。
    - 狀態是「還沒讀到」時，一律回答「還不知道」。
  - **標記動作的本體**（03 號票第二輪 review 後從圖層抽過來，2026-11-10）：見下面「標記動作」。送出請求和套用回覆的函式由圖層注入，所以這個模組照樣不 import 任何東西。抽過來是為了讓「存檔中」防重複送出有測試鎖住。
- 現在的時間一律用伺服器時間（本機時鐘加上偏移），跟圖層既有的到期判斷一致。原站用的是本機時鐘，這裡刻意不一樣。

**花的規則模組（擴充）**

- 新增「**能不能標記拿過精華**」，也就是 Q4 的按鈕條件：點位種類是花、不是花苞、有 id、盛開時間是正整數、枯萎時間是大於 0 的有限數字，而且盛開時間 ≤ 現在 < 枯萎時間。
  - 它跟撈水果的條件不一樣。撈水果在 pipi-fruit-approach 02 號票（`d49d0bc`）之後只對彩帶花，本身就要求有枯萎時間，所以「沒有枯萎時間」已經不是兩者的差別。現在的差別有兩個：
    - 盛開超過 60 分鐘、彩帶期過了的花，可以標記，但不能撈水果。
    - 標記要有 id，盛開時間還要是正整數；撈水果不要求。
  - 盛開時間要是正整數，是為了跟 `PUT` 的驗證一致（見原站協定「送出的值」）。
  - 它放在這裡、不放在拿過精華模組，原因是它要用花苞的規則，而兩個模組都不能在執行期互相 import。測試切面 B、C 的分工因此跟確認時說的略有不同：B 管標記的識別、狀態和過期，C 管按鈕條件。
- 花的子篩選的判斷多收一個參數「這筆點位是不是拿過精華」：拿過、沒拿過或還不知道，由呼叫端用拿過精華模組算好再傳進來。
  - 花的話：沒勾「顯示拿過精華的花」，而且是拿過或還不知道，就不顯示。所以標記清單還沒讀到時，花先不畫（見圖層「標記狀態的生命週期」）。
  - 勾著「顯示拿過精華的花」時沒有東西要藏，還不知道的花照常顯示。
  - 這條跟既有兩條要全部通過，所以拿過精華的彩帶花在「只顯示彩帶」底下也不顯示（Q8）。
  - 蘑菇、煙霧不管這個參數，一律通過。這條放在模組裡、不放在圖層，模組的測試才鎖得住「還沒讀到時蘑菇、煙霧照常畫」。

**花的子篩選設定**

- 設定多一個布林值 `showEssenceTaken`（顯示拿過精華的花），初始值是 false（Q8）。
- 存在既有的 `locwarp.pipi_flower_filter` 物件裡，不另開新的 key。resolver 照既有的規則逐欄還原，所以這個功能之前存的兩欄設定照樣有效，第三欄用初始值。
- 面板：第三個勾選框排在既有兩個後面，縮排相同。「花」關掉時一起變灰，保留勾選值。

**圖層**

- **標記改變時只重畫，不重抓**：標記狀態放進「建立 marker」那個 effect 的相依項，**不能**放進抓資料的 effect，理由跟花的子篩選當初一樣：放進去會讓抓取迴圈重跑、立刻再打一次 items。
- **藏起來的花不佔點位上限**：判斷要不要顯示，是在套點位上限之前做的。
- **✓ 徽章**：拿過精華而且有顯示的花，角落加一個 ✓。
  - 是不是拿過精華，在建立 marker 時判斷，整層重建和重新挑選都算。icon 的快取鍵要包含這一項。
  - ✓ 要放在圖示的外層，跟內層的圓並列。內層是圓形加 `overflow: hidden`，放在裡面的角落徽章會被切掉；彩帶花的彩虹框不用偽元素，也是這個原因。
  - 小、中、大三種尺寸都要清楚，大小跟著標記大小縮放。`--pipi-*` 這幾個 CSS 變數現在是 inline 設在內層 `.pipi-pin-inner` 上，跟內層並列的 ✓ 拿不到，要另外處理。
  - 每 30 秒的 prune 照舊，只看枯萎時間。標記的失效時間就是枯萎時間，所以標記過期的花也會跟著被 prune 拿掉。
- **標記狀態的生命週期**：
  - **還沒讀到時先不畫花**（2026-11-09 review 後使用者確認）：items 和清單同時發出，後端排隊、間隔 1 秒，誰先回來不一定。沒勾「顯示拿過精華的花」時，標記還沒讀到，花就先不畫，蘑菇、煙霧照常畫；清單讀到或讀取失敗之後才畫花。
    - 這樣打開圖層時，拿過的花不會先閃出來、約 1 秒後才消失。代價是花可能比蘑菇晚約 1 秒出現。
    - 勾著「顯示拿過精華的花」時，花照常畫，✓ 等清單回來才出現。
    - 這條靠花的子篩選的「還不知道」來做，不在圖層另外寫判斷。
  - **回到還沒讀到**：圖層關閉、cookie 被清掉時。
  - **舊的標記先留著**：cookie 重新設定、按「重新整理」開始新的一輪時，舊的標記先留著，等新清單回來再整份取代，或讀取失敗時清空。這樣不會有一兩秒的時間，拿過的花全部閃出來。
  - **讀取失敗**（包括 429；cookie 失效或登入錯誤除外，見「讀標記清單的時機」）：清空標記狀態，也就是變成「讀到了、一朵都沒有」，不是「還沒讀到」，所以所有花照常顯示（Q10）。面板狀態列加一行「精華標記讀取失敗」，這一行留到下一次讀取成功，或下一輪開始。
  - **清單內容沒變就不更新**：拿過精華模組回傳原本的狀態物件，圖層就不會多重建一次整層。
- **popup 的按鈕列**：
  - 撈水果和標記兩顆按鈕在同一列，撈水果在左邊，兩顆等寬。只出現其中一顆時，它佔滿整列。兩顆都不出現時，整列不出現。
  - 撈水果只對彩帶花，所以兩顆並排只會出現在彩帶花上，大部分盛開的花只有標記按鈕，佔滿整列。彩帶花很少：pipi-fruit-approach 02 號票實測新竹 344 個 popup，只有 1 朵彩帶花。
  - 按鈕文字在打開 popup 的當下決定，跟既有的剩餘時間一樣。標記狀態是「還不知道」時，用「我拿過精華了」。
  - **動作收整筆點位**：popup 的每個動作都改成收到整筆點位，不再只收座標；瞬移、導航、撈水果從裡面取座標。標記按鈕要有自己的動作對應，遵守既有規則：沒有對應的動作什麼都不做，只記錄一筆錯誤。
    - MapView 現在把收座標的 `onTeleport`、`onNavigate`、`onPipiCollectFruit` 直接傳給圖層。03 號票要在 MapView 把三個都包一層、從整筆點位取座標，build 才會過；04 號票再把撈水果改成整筆一路傳到 App。
  - **各個動作自己決定要不要關 popup**：現在共用的點擊處理會先關掉 popup，再呼叫動作。改成由各個動作決定：瞬移、導航、撈水果照舊先關；標記不關，因為存檔期間要停用按鈕、失敗時 popup 要留著、勾著「顯示拿過精華的花」時 popup 也要留著。
  - **寬度**：實作時要在中文、英文兩種介面下實際看。如果並排會換行，只有同時出現兩顆按鈕的 popup 才加寬，寬到兩顆都不換行；其他花、蘑菇、煙霧的 popup 寬度不變（Q18、Q27）。按鈕文字不改。
    - Leaflet 的 `minWidth`、`maxWidth` 在建立 marker 時就固定了，有沒有兩顆按鈕卻要到打開 popup 時才知道，所以不能只靠這兩個選項。而且 `maxWidth` 現在是 280，會把內容夾住，英文的兩顆按鈕很可能超過。
    - 做法：同時有兩顆按鈕時，popup 內容加一個 class 撐開最小寬度；花的 marker 的 `maxWidth` 放寬到容納得下。放寬上限只影響內容本來就超過 280 的 popup，所以要實際看過沒有兩顆按鈕的花 popup，寬度沒變。

**讀標記清單的時機（抓取 planner，Q11、Q20）**

- planner 多兩個操作：
  - **「現在要讀標記清單嗎」**：帶入這次的決定，只要不是 hide，而且這個 planner 還沒記下讀過，就回答要。
  - **「這一輪讀過了」**：記下之後，這個 planner 不會再回答要。
- **對上 Q11 的三個時機**：planner 每一輪抓取迴圈建立一次。開圖層、cookie 重新設定、按「重新整理」都會開始新的一輪，所以這三個時機會自然對上。
  - 「cookie 重新設定」指 `updated_at` 改變，也就是擴充套件推送或手動貼上。
  - 原站用 Set-Cookie 替 cookie 續期（後端套用的 renewal）不會改 `updated_at`，也不會開始新的一輪，所以不重讀清單。
- **cookie 狀態確定了才讀**：只有圖層確定有 cookie（`configured` 是 true）的那一輪才讀清單。
  - 原因：圖層一打開時還不知道有沒有 cookie（`configured` 是 null），抓取迴圈照樣會先跑一輪；狀態回來變成 true 時，又開始新的一輪。
  - 圖層開關存在本機，所以 app 啟動時圖層常常已經開著。不擋的話，每次啟動清單都會讀兩次，而且清單不快取，兩次都會打到原站。
- **一輪最多讀一次**：
  - 60 秒的強制刷新、平移、縮放、從 hide 縮放回來都屬於同一輪，不再讀。
  - 第一個決定是 hide（zoom 15 以下）時不讀，要等到第一個不是 hide 的決定才讀。
- **一輪讀不了就等下一輪**：迴圈因為 cookie 失效或登入錯誤停下來時，不送清單請求，也不記成讀過，等下一輪重新開始再讀。
- **429 不算讀過**（2026-11-09 review 後使用者確認，是 Q10 的例外）：
  - 原因：後端的退避時間不會隨著每一輪重設，前端的退避時間卻會。所以在退避期間開始新的一輪（例如按「重新整理」），清單請求會馬上被後端擋回 429，根本沒打到原站。照原本「失敗也算讀過」的規則，這一輪就再也不讀，退避可能長達好幾個小時，拿過的花會一直跑出來。
  - 清單收到 429 時不記成讀過，抓取迴圈的退避時間也照這次的 `retry_after` 設定，跟 items 收到 429 一樣。
  - 退避期間不送清單請求。退避結束後，下一個不是 hide 的決定就再讀，不論那個決定要不要重抓 items。
  - 畫面照讀取失敗處理：清空標記狀態、顯示提示，所以退避期間花照常顯示。
- **其他失敗算讀過**：429 以外的讀取失敗記成讀過，下一輪才會重試，同一輪內不重試（Q10）。
- **清單收到 cookie 失效或登入錯誤**（01 號票 code review 後補，2026-11-09 使用者確認，是 Q10 的例外）：跟 items 收到一樣，抓取迴圈停下來，不算讀取失敗。
  - 原本的 spec 沒寫到這個情況：「迴圈停下來時不記成讀過」講的是停下來之後不送清單；照 Q10 的字面，登入錯誤也算讀取失敗。
  - 原因：清單跟 items 同時發出，items 讓迴圈停下來時，清單通常也收到同樣的錯誤。照「讀取失敗」處理的話會清空標記，按「重新整理」時，拿過的花會在還畫著的舊資料上全部跑出來。
  - 所以標記狀態不動、不顯示「精華標記讀取失敗」、不記成讀過，跟「迴圈停下來時不記成讀過」一致。面板顯示登入錯誤，下一輪重新讀。
- 清單請求跟 items 請求可以同時發出，後端會排隊、間隔 1 秒。這一輪結束（圖層關掉、cookie 重新設定、按重新整理）之後才回來的結果直接丟掉。

**標記動作（手動和自動共用一個）**

- 圖層提供一個標記動作，輸入一筆花和要標記或取消。手動按鈕和自動標記都呼叫它。圖層有沒有開都能用（Q26）。
- **只做四件事**：送出請求、管「存檔中」清單、用回覆更新標記狀態、回傳結果。結果分成三種：成功、失敗（帶原因）、存檔中所以忽略。
- **不關 popup、不跳提示**：這兩件交給呼叫端，也就是手動按鈕和自動標記。原因：
  - 共用動作如果在成功時關 popup，自動標記成功時就會把使用者當下開著的 popup（別朵花，甚至書籤）關掉，圖層關著時也一樣。
  - 兩邊都跳提示的話，後一個會蓋掉前一個。
- **防重複送出**：標記動作自己記一份「存檔中」的識別清單。同一朵花還在存檔中，再呼叫就直接忽略，不送第二次，回傳「存檔中所以忽略」。
  - 光靠停用按鈕擋不住：存檔期間如果剛好遇到 60 秒刷新或清單回來，整層會重建，popup 重開後按鈕又能按。
  - 這份清單不放進 React state。放進 state 的話，每次進入、離開存檔中，都會多重建一次整層。它由拿過精華模組的標記動作自己持有，圖層只建立一個。
- **接受 popup 關掉再重開**：標記狀態是建立 marker 那個 effect 的相依項，所以每次標記成功都會整層重建。開著的 popup 會被關掉，再靠既有的機制重開。
  - 現在每 60 秒刷新資料時就是這樣，這裡不另外做就地更新。
  - 重開時 popup 內容照新的標記狀態重畫，按鈕文字和 ✓ 會一起更新。
- **手動（Q6、Q9）**：
  - 點下標記按鈕時不先關 popup（見圖層「popup 的按鈕列」）。
  - 存檔期間按鈕停用：點下時直接把按鈕設成停用；popup 每次打開，包括整層重建後重開，都讀「存檔中」清單，存檔中的花，按鈕畫成停用。
  - 成功之後：
    - 沒勾「顯示拿過精華的花」時，開著的 popup 正是這朵花的話就關掉，花消失。存檔期間使用者可能已經改開別朵花或書籤的 popup，那個不關。
    - 有勾時，popup 不關，整層重建後重開，按鈕變成「已拿過精華（取消）」，花加上 ✓。這一點原站也是同樣的行為。
    - 取消成功後，popup 一樣不關，按鈕變回、✓ 拿掉。
    - 提示「已標記為拿過精華」或「已取消拿過精華標記」。
  - 失敗時跳出錯誤提示（介面文字表的「標記失敗」「取消失敗」）；popup 還開著的話，按鈕恢復可按。popup 不關，標記狀態不變，不自動重試。這朵花從「存檔中」清單拿掉是共用動作的事。
  - 存檔期間按鈕是停用的，正常不會收到「存檔中所以忽略」；收到時不跳提示。
  - 登入過期時不另外停掉抓取迴圈，下一次抓資料時它自己會發現。
  - **接受的邊界**（2026-11-09 使用者確認）：勾著「顯示拿過精華的花」、標記狀態還沒讀到時標記成功，套用之後仍然是還沒讀到，狀態物件沒變，所以不會整層重建。開著的 popup 按鈕會一直停用，等清單回來、整層重建才恢復。這只會發生在打開圖層後、清單回來前那 1～2 秒，不另外處理。
- **提示**：
  - 由呼叫端跳，沿用 app 既有的單一 toast，新的會蓋掉舊的。面板不顯示被藏掉的花有幾朵（Q13）。
  - 顯示 toast 的函式在 App，圖層拿不到。由 App 經 MapView 把它傳進圖層。

**自動標記（撈水果加上抵達監看，Q17、Q22～Q26）**

- **記下那一朵花**：popup 的撈水果動作已經收到整筆花（見圖層「popup 的按鈕列」），再把它一路帶到 App 的撈水果，不再只帶座標。自動標記用的是按下那一刻的這筆花（Q24），不受走路期間資料刷新的影響。
- **抵達監看是純函式**，放在撈水果模組裡。
  - **輸入**：要走的裝置清單和花的座標。
  - **運作方式**：一筆一筆餵進 WS 事件和當下時間，它回答「還在等」「全部抵達」或「已取消」。後兩種是最終結果，之後再餵事件也不會改變。
  - **事件怎麼對到裝置**：
    - 模擬引擎送出的事件（`state_change`、`navigation_complete`）都帶 `udid`。
    - `device_disconnected` 有兩種形狀：USB 拔掉、裝置掉線時只帶 `udids` 陣列；WiFi 通道停掉、使用者斷線時，`udid` 和 `udids` 都帶。
    - `udids` 是陣列就用它，不是才用 `udid`。結果是空的（`udids` 是空陣列，或兩個都沒有）時，當成所有裝置都斷線。前端既有的裝置清單處理（`useDevice.ts`）也是這樣。後端目前不會送出空陣列。
  - **每台裝置的規則**：
    1. **等開始**：收到 `state_change`、狀態是導航、而且終點等於這朵花之前，其他事件一律忽略。這樣才不會把「停掉上一段走路」送出的 idle 誤認為中途停止。
    2. **走路中**：
       - 只有 `navigating`、`paused` 算還在走。狀態在這兩者之間切換都還在等，所以暫停再繼續不會取消（Q22）。
       - 收到 `navigation_complete` 而且終點等於這朵花，就算抵達。
       - 走路中收到 `navigation_complete` 但終點不是這朵花、收到 `state_change` 變成 `navigating`、`paused` 以外的任何狀態、收到對到這台裝置的 `device_disconnected`，都算取消。
       - 「以外的任何狀態」包括 idle、斷線，以及 teleporting、joystick、looping、`reconnecting` 等。後端換模式之前會先 `stop()` 送 idle，所以現在 idle 和斷線以外的狀態不會直接出現；用白名單是為了以後新增的狀態。
    3. **已抵達**：抵達之後緊接著的 idle 不影響結果。
  - **群組**：每台裝置都抵達，才算「全部抵達」。任何一台取消，整個就取消（Q23）。
  - **忽略無關事件**：不在清單裡的裝置送來的事件一律忽略。
  - **開始的期限**：從建立監看算起（也就是送出導航前一刻，見「接線」）15 秒內，有任何一台還沒開始走，就算取消。這是為了避免導航沒真正開始時，監看一直掛著；否則之後用「導航到這裡」走到同一朵花，會誤觸標記。
    - **判斷順序**：每餵一筆事件，先檢查期限，再處理事件。期限過了還有裝置沒開始，結果就是取消，這一筆事件不看。所以 15 秒後才到的開始事件判成取消，不會當成開始。
    - 原因：監看只在收到事件時往下判斷。少了這個順序，一個一直沒收到開始事件的監看，20 分鐘後還會接受一個開始事件，期限就形同虛設。
  - **終點比對**：座標差在 1e-6 度以內算相等。後端回傳的終點就是前端送出的座標。
- **接線**：
  - 監看在 `runFruitApproach` 的導航 callback 裡、送出導航**前一刻**才建立；群組模式在 150 ms 的等待之後。
    - 不能等導航 API 回覆之後才建立，因為開始走的事件可能比回覆更早到。
    - 也不在瞬移之前建立，否則 15 秒的期限會把瞬移和等待的時間算進去。
    - 瞬移失敗、撈水果中止時，不會呼叫導航 callback，所以根本不會建立監看。
  - 導航沒有開始時，丟掉監看。
  - 群組模式只要有任何一台導航沒送成功，也丟掉監看，不自動標記。
  - 監看有了最終結果（全部抵達或已取消）之後就丟掉。
  - 監看只存在前端的記憶體裡，重新整理頁面就沒了（Q26）。
  - **WS 一斷線就丟掉所有監看**，不等重連。斷線期間的事件收不到，如果剛好漏掉 `navigation_complete`，監看會一直停在走路中。之後裝置閒置時用「導航到這裡」走到同一朵花，停掉上一段走路不會送 idle（裝置本來就閒置），新的開始和完成就會被當成抵達，誤標一次。
  - **App 怎麼叫圖層標記**：WS 訂閱和撈水果都在 App，標記動作、標記狀態和伺服器時間偏移都在圖層裡。
    - MapView 建好地圖時會交給 App 一個地圖介面，現在有平移和縮放到範圍兩個函式。圖層經由這個介面，多提供一個「自動標記這朵花」的函式。
    - 下面「全部抵達時」的檢查、呼叫標記動作、跳提示，都在這個函式裡做完。App 只在全部抵達時呼叫它，不用另外拿到標記狀態和時間偏移。
    - **透過 ref 讀當下的狀態**：MapView 只在建立地圖時呼叫一次 `onMapReady`，交出去的函式不會再換。所以這個函式要透過 ref 讀圖層當下的標記狀態、時間偏移和 toast 函式，不能閉包建立地圖那一刻的值。
      - 閉包舊值的話，標記狀態會一直是那一刻的「還沒讀到」，照「還不知道當成還沒拿過」每次都送，不會報錯，user story 27 就壞了。
      - 這段接線沒有自動化測試，靠人工驗證的 user story 27 那一項。
- **全部抵達時**：用當下的伺服器時間檢查兩件事：花的規則模組說「能標記」，而且拿過精華模組沒有說「拿過」。兩者都成立，才呼叫標記動作；否則直接跳過，不跳提示（Q24）。
  - 「還不知道」當成還沒拿過，照樣標記。圖層在途中被關掉時，標記狀態會回到還沒讀到，這時還是要標（Q26）。
  - 伺服器時間用圖層最近一次的偏移；圖層已經關掉、沒有資料時，直接用本機時鐘。
  - 成功時提示「已自動標記為拿過精華」；失敗時提示原因，不重試（Q25）。沒有 cookie 也算失敗，照樣提示。
  - 標記動作回「存檔中所以忽略」時（例如走路途中自己按了、還在存檔），不跳提示，也不當成失敗（user story 27）。
  - 自動標記不關 popup，使用者當下開著的 popup 不受影響。
  - 在 LocWarp 以外（例如手機上）剛標過、LocWarp 還沒重讀的花，會再送一次 `set`。標記本來就是同一個結果，重送沒有壞處。
- 最近地點、瞬移、導航的既有行為都不變。

## Testing Decisions

**怎樣算好的測試**

- 只透過模組對外的函式測試，驗證行為：哪些花會顯示、算不算拿過精華、什麼時候算抵達、什麼時候要讀清單。不測內部的中間值。
- 盡量用真實的格式：2026-11-05 抽樣的花點位資料，以及 01 號票實測得到的標記清單格式。真實資料測不到的規則可以用合成資料，但測試名稱要寫明它在防哪一種原站格式變化或時序。
- 測試名稱用繁體中文寫出要守住的意圖，比照既有的前端測試。
- 每一條規則都要過 mutation check：改掉那條規則，至少要有一個測試變紅。實作完成時逐條回報。
- 時間一律從參數傳進去，不讀系統時鐘。

**A. 後端 client（新增一支 `tests/pipi/` 測試）**

做法比照 `tests/pipi/test_items_min_zoom.py`：把 `request` 換成假的，記下每次的呼叫，不連網路。

- **讀清單**：送到標記端點，payload 剛好是 `{action: "list"}`。正規化要做到：
  - 數字 id 轉成字串，去掉頭尾空白。
  - id 是空的、盛開時間是 0、盛開時間是字串的那一筆丟掉。
  - 失效時間沒有值時填 0。
  - 回覆沒有 `items` 清單時報 `pipi_unavailable`；`items` 是空清單才是一筆都沒有。
- **設定**：payload 帶原始型別的 id、盛開時間和 `collected`，並回傳 `mark.wiltingTimeMs`；回覆裡沒有 `mark` 時回傳 0。
- **不快取**：連續呼叫兩次，假的 `request` 被呼叫兩次。
- **錯誤**：讀清單和設定兩個方法都要測，`PipiError`（例如 `pipi_login_required`）照原樣往外拋。
- **API body 驗證**：有不合格欄位的 body 被拒絕，而且不會呼叫 client。用暫時的 `SETTINGS_FILE`，比照 `tests/pipi/test_api_cookie.py`。

**B. 拿過精華模組（新增一支 `tests/frontend/` 測試）**

- **識別**：
  - 數字 id 和同值的字串 id 得到同一個識別。
  - 頭尾空白被去掉；盛開時間的小數被捨去。
  - id 是空的、盛開時間是 0、負數或字串時，沒有識別，所以永遠不算拿過。
- **過期邊界**：失效時間大於現在算拿過；等於現在不算；是 0 不算。
- **重新開花**：同一個 id、不同的盛開時間，不算拿過。
- **還沒讀到**：狀態是還沒讀到時，每一朵花都回答「還不知道」；讀到了、一朵都沒有時，回答「沒拿過」。這一條防的是一朵都沒標過的帳號，花永遠畫不出來。
- **清單整份取代**：
  - 舊狀態裡有、新清單裡沒有的標記會消失。
  - 新清單的內容跟舊狀態一樣時，回傳原本那個狀態物件；不一樣時回傳新的。舊狀態是還沒讀到時，一律回傳新的。
- **設定回覆**：
  - 標記時用回覆的失效時間；回覆是 0 時改用花的 `wiltingMs`。
  - 取消時刪掉這個識別。
  - 舊的狀態物件沒有被改動。
  - 套在還沒讀到的狀態上，結果仍然是還沒讀到。
- **標記動作**（03 號票第二輪 review 後補，2026-11-10）：
  - 同一朵花存檔中再呼叫：回「存檔中所以忽略」，不送第二次，標記和取消都是。
  - 只擋同一次開花：別朵花、同一個花點的下一次開花照樣送出。
  - 送出點位原本的 id 和盛開時間；回覆回來才套用，用回覆的失效時間。
  - 送出失敗：回失敗和原因，不套用、不重試；之後同一朵可以再送。成功之後也可以再送。
  - 沒有識別的點位：回失敗，不送出。

**C. 花的規則模組與初始值（擴充既有的 `tests/frontend/test_pipi_flowers.ts`、`tests/frontend/test_defaults.ts`）**

- **能不能標記**：
  - 盛開時間剛好等於現在可以；早於盛開時間不行；剛好到枯萎時間不行。
  - 沒有枯萎時間不行。撈水果也一樣不行，所以這一條鎖的是標記自己的條件，不是兩者的差別。
  - 盛開 61 分鐘、彩帶期過了的花能標記、不能撈水果，這是跟「能撈水果」的差別，要有一個測試鎖住。
  - 盛開時間有小數不行，跟 `PUT` 只收正整數一致。
  - 三種寫法的花苞都不行；沒有 id 不行；蘑菇、煙霧都不行。
- **花的子篩選第三條**：
  - 拿過精華的花：沒勾就藏，勾了就顯示。沒拿過的花不受影響。
  - 還不知道的花：沒勾就藏，勾了就顯示。
  - 拿過精華的彩帶花在「只顯示彩帶」底下：沒勾第三條就藏，勾了就顯示。
  - 蘑菇、煙霧就算傳入「拿過精華」或「還不知道」，也照樣顯示。
  - 把既有的真值表擴充成三個子選項的八種組合，每種組合都測拿過、沒拿過、還不知道三種狀態。
- **初始值**：
  - 沒存過時，第三欄是 false。
  - 只有兩欄的舊 JSON，兩欄保留，第三欄是 false。
  - 第三欄不是布林值時，用初始值。

**D. 抵達監看（擴充既有的 `tests/frontend/test_pipi_fruit.ts`）**

用合成的 WS 事件序列，形狀照後端實際送出的事件。

- 單機：開始 → `navigation_complete`（終點是這朵花），算抵達。
- 暫停 → 繼續 → 完成，還是抵達。
- 開始之後、完成之前收到 idle，算取消；收到斷線，也算取消。
- 開始之後收到 `navigating`、`paused` 以外的狀態（例如 teleporting），算取消。這一條防的是以後新增的狀態被當成還在走。
- `device_disconnected` 各種形狀都要測，開始之後收到都算取消：
  - 只帶 `udids`（USB 拔掉、裝置掉線的形狀）。
  - 同時帶 `udid` 和 `udids`（WiFi 通道停掉的形狀）。
  - 兩個都沒有：當成所有裝置都斷線。
  - `udids` 是空陣列：一樣當成所有裝置都斷線，跟 `useDevice.ts` 一致。後端目前不會送出這個形狀。
  - `udids` 裡沒有清單裡的裝置時，不影響結果。
- 開始之前收到 idle，被忽略，之後正常開始、完成，還是抵達。這一條防的是「停掉上一段走路」被誤判。
- 完成時終點不是這朵花，算取消。
- 抵達之後緊接著的 idle，結果仍然是抵達。
- 群組：兩台都完成才抵達；只有一台完成時還在等；一台取消就整個取消。
- 不在清單裡的裝置的事件，不影響結果。
- 過了 15 秒還有裝置沒開始，算取消；15 秒內開始，就不受影響。
- 15 秒後才收到開始事件，算取消，不當成開始。這一條防的是之後用「導航到這裡」走到同一朵花時誤標。
- 最終結果之後再餵事件，結果不變。

**E. 抓取 planner（擴充既有的 `tests/frontend/test_pipi_fetch_planner.ts`）**

- 新的 planner 在第一個不是 hide 的決定時，回答要讀。
- hide 時一律回答不讀；先 hide、再縮放回來，在縮放回來那個決定才回答要讀。
- 記下讀過之後，同一個 planner 遇到強制刷新、平移、縮放回來，都不再回答要讀。
- 新的 planner（新的一輪）又會回答要讀。

**人工驗證（沒有自動化，要逐項回報）**

repo 沒有前端 DOM 測試環境，下面這些在真實的 app 裡操作確認。要模擬失敗時，另開第二個 Vite（例如 port 5174），在 app 的程式碼載入前先注入 fetch 攔截，讓指定的 `/api/pipi/essence` 請求失敗。

- **哪些請求可以打到原站**：
  - 設定請求（`PUT /api/pipi/essence`）只放行兩次：下面「實際打原站」的那一次標記和一次取消（03 號票），以及 04 號票「單機實際撈水果一次」那次的自動標記。動手前都要先跟使用者說是哪一朵。
  - 其他的設定請求一律由攔截器回假的 `{wiltingMs}`。連點、延遲加重新整理、成功後花消失、有勾時出現 ✓ 這些需要「標記成功」的項目，都用假的成功。
  - 用攔截器改 items 的 `bloomedMs` 造彩帶花時，設定請求**絕對不能放行**，否則假的盛開時間會寫進使用者的原站帳號。
  - 瞬移、導航這些會移動實機的請求：03 號票用不到實機，比照 01 號票在瀏覽器攔下，只記下送出的內容。04 號票的真機驗證要讓它們送出去，動手前先跟使用者說。
- **實際打原站**（使用者已經同意，Q12）：
  - 要先用 `start.py` 把 LocWarp 跑起來，走後端自己的 client。
  - 先讀一次清單，把實際格式記下來。
  - **交叉比對**：拿使用者標過的那朵花，確認清單裡的 `(mapObjectId, bloomedTimeMs)` 跟 items API 的 `(id, bloomedMs)` 對得上，算出來是同一個識別。整個「藏起拿過的花」都靠這一點成立。
  - 同時記下 items 裡 id 和盛開時間的實際型別（見原站協定「送出的值」）。
  - 再挑一朵盛開中的花，標記一次、馬上取消。動手之前要先跟使用者說是哪一朵。
  - 在手機或原站上確認標記確實出現過，最後也確實取消了。
- **popup**：
  - 中文、英文介面下的並排和換行；需要加寬時，只有同時出現兩顆按鈕的 popup 變寬，沒有兩顆按鈕的花 popup 寬度沒變。
    - 兩顆並排只出現在彩帶花上，實際幾乎碰不到，要事先計畫用攔截器改 items 的 `bloomedMs` 造一朵。這朵花的設定請求一定要攔下（見「哪些請求可以打到原站」）。
  - 只出現其中一顆按鈕時，它佔滿整列。
- **面板**：第三個勾選框的排版；「花」關掉時變灰並保留勾選值；重新整理頁面後設定還在。
- **標記與取消**：
  - 沒勾第三條時，標記成功後 popup 關掉、花消失。
  - 有勾時，popup 不關，出現 ✓ 和取消按鈕；取消之後 ✓ 消失。
  - 三種標記大小下都看得到 ✓，而且沒有被圖示的圓切掉。
  - 狀態列筆數等於實際的 marker 數。
  - **存檔中**：用攔截把設定請求延遲幾秒。延遲期間連點只送出一次；延遲期間按「重新整理」讓整層重建，popup 重開時按鈕還是停用。
- **還沒讀到時先不畫花**：
  - 用攔截把清單回覆延遲幾秒，打開圖層：蘑菇、煙霧先出現，花等清單回來才出現，拿過的花全程沒出現過。
  - 同樣延遲，按「重新整理」：舊的標記留著，拿過的花在延遲期間也沒出現。
- **失敗**：
  - 用攔截讓標記請求失敗：出現錯誤提示、按鈕恢復、花沒有被藏。
  - 用攔截讓清單請求失敗：所有花都顯示、面板出現讀取失敗的提示。
  - 用攔截讓清單請求回 429、`retry_after` 設成幾秒：所有花都顯示、面板出現提示；退避結束後的下一次抓取，又送出一次清單請求。
- **Network 請求數**：
  - 打開圖層、按重新整理、cookie 重新設定時，各有一次清單請求。
  - 圖層開著時重新整理整個頁面（app 啟動時圖層已經開著），只有一次清單請求。
  - 60 秒自動刷新、平移、縮放都沒有清單請求。
  - 在 zoom 15 以下打開圖層時沒有清單請求，縮放到 15 才有。
  - 自己按標記之後，沒有清單請求。
- **自動標記**：
