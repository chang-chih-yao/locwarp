# 01 蘑菇地圖的點位上限照回傳順序截斷，畫面內的點位可能被丟掉，面板也不提示

Status: resolved
Blocked by: (none)
Type: bug

## 現象

- 圖層建立 marker 時，畫滿 1500 個就停，順序是原站 `items` 陣列的順序，跟點位離畫面多近無關（`frontend/src/hooks/usePipiMushroomLayer.ts` 建 marker 的迴圈開頭，`MAX_MARKERS`）。
  - 只有實際畫出來的點位才計入上限：點位種類關掉的、已結束的、被花的子篩選拿掉的，都不佔名額（`.scratch/pipi-flower-filter/spec.md` 的決定）。
- 抓取範圍是畫面往外 pad 25%，面積約為畫面的 2.25 倍。所以畫出來的 1500 個裡有不少在畫面外，畫面內的點位反而可能被截掉。
- 面板「這個範圍資料太多, 只顯示部分, 放大可看完整資料」只在原站回傳的 `truncated` 為 true 時出現，上限截斷不會觸發它。狀態列只顯示畫出來的筆數，使用者看不出少了點位。

## 量到的數據

- 2026-11-05 下午，透過本機 backend 打 items API。條件是台北車站一帶（25.0478, 121.5170）、zoom 15，以 1400×850 的畫面往外 pad 25%：
  - 原站回 2191 筆：花 1578、蘑菇 577、煙霧 36。`truncated` 是 false，也就是原站沒有截斷。
  - 開著花時，扣掉已結束的點位仍超過 1500，會被 LocWarp 截掉。
  - 只開蘑菇時（初始值）是 577 筆，碰不到上限。
- 同一天做花的子篩選人工驗證時（`.scratch/pipi-flower-filter/spec.md` 底部 Comments），真實資料有 2817 筆、原站沒有截斷，藏起普花後非普花的 1153 朵全畫出來了。依此推算，沒藏普花時一樣會撞到上限。這是推論，當時沒有直接記錄被截掉的筆數。

## 待 triage 決定

已在 2026-11-05 triage 決定，結果見 Comments 的 Agent Brief；下面保留原始的問題清單當背景。

- 截斷時要不要在面板提示：跟原站截斷共用同一句，還是另寫一句。
- 截斷時保留哪些點位：
  - 照回傳順序（現況）。
  - 畫面內的優先。
  - 離畫面中心近的優先。
  - 如果改成依畫面挑選，平移時沿用資料、沒有重抓的情況也要重新挑。這會改到畫 marker 的那段，不會改到 `.scratch/pipi-zoom-threshold/` 新增的抓取判斷模組。
- 要不要調整 1500：
  - 現在每個點位都是一個 DivIcon，也就是一個 DOM 元素，調高要先量效能。
  - 原站在 zoom 16 以上的畫面標籤寫「Canvas 圖標模式」（`.scratch/pipi-zoom-threshold/spec.md`），推測是用 Canvas 畫點位（例如 Leaflet 的 `preferCanvas`），所以沒有同樣的 DOM 數量問題。是否真的用 `preferCanvas` 沒有驗證過。這可以當成另一個方向參考。
- 這個上限是 LocWarp 自己的渲染上限，不是對原站的節流。`.scratch/pipi-zoom-threshold/` 會在規則檔寫明「對原站的節流只能收緊」，這條不適用於它。

## Comments

### 2026-11-05 triage：Agent Brief

> *This was generated by AI during triage.*

**Category:** bug
**Summary:** 發生上限截斷時，改成照「畫面框距離」保留離畫面中心最近的點位、打開中 popup 的點位額外保留、平移停下後以差異更新重挑，並只在畫面內缺點時於面板提示；不再照原站回傳順序靜默截掉

用語照 `GLOSSARY.md`：**點位上限**、**原站截斷**、**上限截斷**、**畫面內缺點**。本 brief 另用一個實作用語，並寫明畫面內缺點怎麼判定：

- **畫面框距離**：點位相對畫面中心的位移，依畫面長寬換算後取較大的一邊，即 `max(|dx| / (W/2), |dy| / (H/2))`。`dx`、`dy` 是投影後的畫面像素位移，`W`、`H` 是地圖容器的像素寬高。畫面內的點位此值 ≤ 1，畫面外的 > 1。
- **畫面內缺點**的判定：畫面框距離 ≤ 1、該顯示的點位中，有沒畫出來的。照下面的挑選規則，這幾乎等同於「畫面框距離 ≤ 1 的該顯示點位超過點位上限」，只有一個例外：畫面內剛好多一個、多出來的那個正好是額外多畫的打開中 popup 點位。這時畫面內已全畫出來，不算畫面內缺點。

triage 時已用程式碼確認現象（沒有重打原站 API，數據沿用上方「量到的數據」）。

**Current behavior:**

- `usePipiMushroomLayer` 建 marker 時照 `res.items` 的順序逐筆判斷點位種類、到期、`passesFlowerFilter`，通過的才畫，畫滿 `MAX_MARKERS`（1500）就 break。跟點位離畫面多遠無關；原站 `items` 的排序沒有記錄，若是依點位種類分組，可能整種點位都畫不出來。
- 抓取範圍是畫面往外 pad 25%，所以畫出的 1500 個有不少在畫面外，畫面內的反而可能被截掉。
- 面板的黃色提示（`map.pipi_truncated`）只看原站回傳的 `truncated`，上限截斷不會觸發任何提示；狀態列「顯示 N 筆」只反映畫出來的筆數。

**Desired behavior:**

- **挑選規則**：該顯示的點位（點位種類有開、尚未結束、通過花的子篩選）超過點位上限時，依畫面框距離由小到大保留，中心取挑選當下的畫面中心。
  - 用畫面框距離而不是直線距離：直線距離挑出的是圓，畫面是長方形，截斷半徑落在中心到上下邊與中心到角落之間時，畫面角落的點會被畫面上下外側的點擠掉。畫面框距離挑出的是跟畫面同比例的長方形，畫面內的點一定先於畫面外的點入選，沒有例外（打開中 popup 的點位是額外加上的，不擠掉任何點位，見下一條）。
  - 點位座標要用加上 `lngShift` 之後的經度（跟畫 marker 用的座標一致）。
  - 不分點位種類，統一照畫面框距離排，不設配額。
  - 畫面框距離相同時維持回傳順序（穩定排序），讓結果可預期。
  - 未超過上限時全部照畫，行為跟現在一樣。
- **打開中的 popup**：先照上面的規則挑出前 N 個（N 是點位上限）。若有打開中的 popup，它的點位不在這 N 個裡、而且通過判斷函式，就**額外多畫它一個**，不擠掉任何點位，所以畫出的總數最多是點位上限加 1。
  - 它本來就在這 N 個裡時，不另外加，也不擠掉別人。
  - 它已結束、被篩掉、或不在這批資料裡時，照常不畫。
  - 額外多畫的這一個不影響上限截斷的判定。畫面內缺點照上面的定義，看實際畫出的點位：它若正好是畫面內唯一沒入選的點位，畫面內就全畫出來了，不算畫面內缺點。狀態列「顯示 N 筆」照實際畫出的筆數，可能是點位上限加 1。
  - popup 的 id 從哪讀：整層重建時沿用現有的 reopen 機制，讀 `reopenIdRef`（cleanup 先把 id 存進去，因為接著 `layer.remove()` 觸發的 popupclose 會把 `openIdRef` 清成 null）；重挑沒有 cleanup，讀 `openIdRef.current`。
- **重挑**（同一批資料、畫面換了位置）：
  - 時機：由抓取迴圈的 `load` 觸發。`load` 問完 `createPipiFetchPlanner` 之後，只要決定不是 `hide`，就呼叫重挑，排在停止抓取、reuse、要重抓、429 back-off 這些判斷之前。只有點位有顯示、而且上一次挑選發生了上限截斷時才真的重挑，以當下的畫面中心重新挑。
    - 所以重挑跟抓取判斷共用同一個 700 ms debounce，切回視窗與 60 秒強制刷新時也會跑。不另外掛 moveend listener 或 timer：兩個 debounce 的先後不固定（Leaflet 照註冊順序觸發 listener，抓取 effect 重跑後順序就會反過來），縮到門檻以下時重挑可能比 hide 先跑。這樣藏不藏起來也只由 planner 決定，跟 `.scratch/pipi-zoom-threshold/spec.md`「藏起來和重畫跟抓取在同一個地方判斷」一致。
    - **不看 planner 除了 `hide` 以外的決定**：reuse、要重抓、被 429 的 back-off 擋下、cookie 失效停止抓取、請求失敗時都一樣重挑。
    - 要重抓時，會先用舊資料重挑一次，新資料回來再整層重建一次；這可以接受。
    - 點位被藏起來（`hide`）時不重挑；從藏起來恢復時本來就會整層重建，不需要另外重挑。
    - 重挑的函式由 marker effect 提供（例如放進一個 ref 給 `load` 呼叫）。marker effect 的 cleanup 要把它清成 null，點位藏起來、沒有資料、圖層關閉時才不會呼叫到舊的圖層。
  - 時間：判斷函式用**重挑當下**的伺服器時間（`Date.now() + offset`），不沿用整層重建時算的 `now`。沿用的話，prune 已拿掉的點位會被重挑加回來，30 秒後又被拿掉。由此帶出的行為都是預期的：
    - 整層重建之後才結束的點位，重挑時就拿掉，不用等 prune。
    - 開著「只顯示彩帶」時，彩帶期已過的花在重挑時就消失，不用等下一次整層重建。
    - 留下來的 marker 保留建立時的彩虹圓環判定，重挑新加入的用重挑當下的判定，兩者最多並存到下一次整層重建（60 秒內）。`usePipiMushroomLayer.ts` 彩虹圓環那行的註解「Decided per rebuild only」要改成「marker 建立時（整層重建或重挑）判定，prune 不重新判定」。
  - 做法：**依 id 差異更新**。仍在名單上的 marker 原樣保留，只移除掉出名單的、加入新入選的。打開中 popup 的點位一定在名單上，所以它的 marker 不會被移除，popup 不會被關掉再打開，也就不會觸發 Leaflet popup 的 autoPan 把地圖拉回去。
  - 每次重挑都寫入 status 的 `shown`（實際畫出的筆數）與畫面內缺點的欄位。
  - 沒有上限截斷時，平移停下不動圖層。
  - 重挑不送任何 items 請求，也不改變抓取判斷模組的任何決定。
- **整層重建**：資料、點位種類、花的子篩選、標記大小改變時，照現在的方式整層重建，挑選用重建當下的畫面中心與伺服器時間。
- **prune**：照舊每 30 秒拿掉到期的 marker，不重新挑選、不重新判定提示。prune 之後狀態列的筆數可能低於點位上限，要等下一次重挑或重建才補回；這是預期行為，不是 bug。重挑後新加入的 marker 一樣要能被 prune，已移除的不能再被 prune 計數。
- **提示**：
  - 新增一句 i18n（建議 key `map.pipi_capped`），`{count}` 填點位上限的數字：
    - zh：「這個畫面的點位超過 {count} 個, 只畫出靠近中心的部分, 放大或少開幾種點位可看完整資料」
    - en：「More than {count} points in view, showing those nearest the center; zoom in or turn off some kinds for the full set」
  - **只在畫面內缺點時出現**。整批有上限截斷、但畫面內該顯示的點位全畫出來時不出現。所以放大後停下會重挑，畫面內不再缺點時提示就消失，不必等 60 秒刷新。
  - 每次整層重建與每次重挑時判定；prune 不重新判定。
  - 顯示條件另需跟原站截斷提示相同：圖層開著且 phase 為 `ok`。點位被藏起來、圖層關閉、沒有資料時一律不顯示。
  - 兩種提示同時成立時兩句都出現，原站截斷在上、這句在下，外觀沿用現有的黃色提示框。
- **狀態列**：維持「顯示 N 筆」，不加總數。
- 剛好等於點位上限不算上限截斷。

**Key interfaces:**

- 新增一個不依賴 Leaflet 的純函式模組（比照 `pipiFetchPlanner.ts`、`pipiFlowers.ts` 的模式），例如 `selectPipiMarkers`：
  - 輸入：原站回傳的**全部**點位、一個由 hook 提供的「要不要顯示」判斷函式（點位種類、到期、花的子篩選）、每個點位的投影座標、畫面中心的投影座標、畫面的像素寬高、點位上限、必定入選的 id（可為 null）。

     - 它本來就在前 N 個裡：結果就是前 N 個，共 N 個，沒有重複的 id。
     - 它被判斷函式擋掉：不在結果裡，結果等於正常挑選。
     - 它的 id 不在資料裡：結果等於正常挑選。

     - 整批超過上限、但畫面內該顯示的點位不超過上限：回報有上限截斷、沒有畫面內缺點。
     - 畫面內該顯示的點位超過上限：回報兩者皆有。
     - 畫面內該顯示的點位剛好等於上限、必定入選的點位在畫面外：畫面內的點位全部入選、再加上它，回報沒有畫面內缺點。
     - 畫面內該顯示的點位比上限多一個、多出來的正好是必定入選的點位：畫面內全部畫出，回報沒有畫面內缺點。

  - 模組改看排序後第一個沒畫出來的點位：通常是第 N+1 個；第 N+1 個是額外多畫的 popup 點位時，改看第 N+2 個。
