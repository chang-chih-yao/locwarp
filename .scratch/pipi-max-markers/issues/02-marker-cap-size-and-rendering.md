# 02 點位上限的數字與渲染方式：量過 DivIcon 效能後，決定調低點位上限（不改 Canvas）

Status: resolved
Blocked by: (none)
Type: enhancement

## 現況

- 點位上限是 1500，LocWarp 自己定的渲染上限，不是對原站的節流。`.claude/rules/pipi-mushroom.md` 寫明它可以往上或往下調。
- 每個點位是一個 Leaflet DivIcon，也就是一個 DOM 元素。裡面有點位圖片或圓點、依點位種類變色的圓環、彩帶花的彩虹圓環（`.pipi-ribbon`），尺寸跟著標記大小（小 30 / 中 40 / 大 50 px）。另外每個點位都綁 tooltip 和 popup。
- 1500 這個數字沒有量測依據。

## 為什麼要處理

- 台北車站一帶、zoom 15、開著花時，該顯示的點位超過點位上限（01 號票量到原站回 2191 筆，其中花 1578 筆）。
- 01 號票做完後，上限截斷時會照畫面框距離挑點：畫面內的點一定先畫，畫面外被截掉的點在平移停下後重挑補上。所以這張票只在**畫面內缺點**時才有必要，也就是畫面內該顯示的點位本身就超過點位上限、面板出現 01 新增的提示時。這種情況要畫得完整，得調高上限或換渲染方式。
  - 上例依平均分布估計，1400×850 的畫面內約九百多個點，不到 1500，不會畫面內缺點。實際多常發生，要等 01 上線後才知道。
- 另一個要處理的情況是 1500 個本身就卡：01 讓有上限截斷時每次平移停下都做一次依 id 差異更新，多了一筆原本沒有的成本。

## 參考

- 原站在 zoom 16 以上的畫面標籤是「Canvas 圖標模式」（`.scratch/pipi-zoom-threshold/spec.md`），推測是用 Canvas 畫點位（例如 Leaflet 的 `preferCanvas`），所以沒有同樣的 DOM 數量問題。是否真的用 `preferCanvas` 沒有驗證過。
- 跟原站比較時條件不同：原站在 zoom 15 只畫 5 分鐘內結束的蘑菇和煙霧，16 以上才畫全部（也就是「Canvas 圖標模式」）；LocWarp 從 15 起就畫全部。zoom 16 的畫面面積只有 zoom 15 的 1/4，原站要同時畫的點位本來就少得多，不能直接拿 DOM 數量比。
- 01 號票的 brief 規定挑選模組以參數收點位上限，所以 01 做完後，改數字不用動挑選邏輯。
  - 01 做完後，打開中 popup 的點位會額外多畫一個，實際最多畫點位上限加 1。

  - 拆解：包住 `L.LayerGroup` 的 `onAdd` 與 `onRemove` 計時。

- 耗時大致跟點位數成正比：改標記大小每個點位約 0.11 ms，資料更新約 0.09 ms。
- 沒量到的：
  - 分頁的 rAF 只有每秒約 1 幀，Chrome 視窗應該被其他視窗蓋住了。所以沒有 paint 和 raster，也沒有以幀計的數字；上面的數字只算到 JS 加強制 style 和 layout，實際只會更長。
  - 平移拖動時的流暢度和縮放動畫沒量。Leaflet 平移時只移動整個 pane，不會逐一移動 marker；縮放動畫在開始和結束時各會逐一重設一次 marker 位置。
  - 資料更新後 0.4–0.6 秒，3 次裡有 2 次另外出現一個約 75 ms 的 long task，來源沒查出來。
  - 量的時候用的是哪個底圖（`locwarp.tile_layer`，可選 MapLibre GL 向量圖），以及 S2 格線、書籤圖釘有沒有開，都沒有記錄。整層重建和重挑只動蘑菇地圖圖層，影響不大；縮放動畫和拖動的幀會受底圖影響。
  - 只量了這台機器。

**結論與考慮過的方向：**

- 1500 會卡，照規則不能 `wontfix`。
- 考慮過但沒採用的方向：
  - 資料更新、切換點位種類與花的子篩選，也改成跟重挑一樣依 id 差異更新：DivIcon 和 1500 都不動，60 秒刷新前後的資料幾乎一樣（2869 筆對 2871 筆），預期能降到重挑的量級。使用者選了調低上限。
  - 改 Canvas：外觀和 tooltip、popup、hover 都要重做。
  - 維持現狀：等於放寬 100 ms 的門檻。
- 調低上限的代價：上限低於 1310 時，台北車站三種全開會出現畫面內缺點的提示。使用者接受這個代價。
- 750 的來由：照 817 個最慢的那次 106 ms 換算（約 0.13 ms 一個），三種整層重建都會在 100 ms 內。因為沒有含 paint，實作時要連 paint 一起驗證。
- 750 的餘裕很小：750 × 106 / 817 ≈ 97 ms，離門檻只差約 3 ms，還沒算 paint。而且 817 個那次沒有上限截斷，挑選模組直接回傳；750 是從 2841 個裡挑，每次整層重建都要對全部 2841 個做投影再排序，會多一點成本（沒量過，推測不大）。所以驗收時第一輪不過、降到 700 是預期內的。
- 不依點位種類或縮放層級設不同的上限：每個 marker 的成本跟點位種類無關，縮放越大畫面內的點位本來就越少，分開設定對這個門檻沒有幫助。這點是 triage 自行判斷的，使用者可以推翻。
- 2500、3000 個的假資料不用量了，因為方向是往下調。

**量測方法參考（給驗收用）：**

- Leaflet 1.9 會設 `window.L`。地圖實例可以從 `.leaflet-container` 的 React fiber 往上找：找 hook state 裡 `current instanceof L.Map` 的那個 ref。
- 量之前先確認 rAF 每秒至少 50 幀（螢幕更新率不是 60 Hz 時，要接近螢幕更新率）。只有每秒幾幀時，表示視窗被蓋住了，量到的數字不能用。
- 視窗在最前面時改用 `long-animation-frame`（LoAF）判斷，它的 duration 包含 render，不能只看 `longtask`。
  - LoAF 只回報超過 50 ms 的幀，沒有紀錄的幀都低於 50 ms。
  - LoAF 只算主執行緒，含主執行緒上的 style、layout、paint，不含 raster 和合成。所以「連 paint 一起驗證」實際上只涵蓋主執行緒的部分，這是這張票接受的範圍。
