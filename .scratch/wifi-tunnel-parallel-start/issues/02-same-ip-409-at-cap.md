# 02 裝置連線：已有 2 條 WiFi 通道時，同一個 IP 同時送兩次，第二個回 409、不是 `already_running`

Status: wontfix
Blocked by: (none)
Type: bug
相關：`.scratch/wifi-tunnel-parallel-start/issues/01-parallel-tunnel-start.md` 實作 Comment「記下、沒修」第 1 條（`:361-364`）。

## 為什麼

01 號票的決定（`:43`）和 brief 的期望行為（`:230`）寫的是：同一個 IP 已有請求在握手時，等它結束再重做開頭那段；「它成功的話，這次就會走到 `already_running`」。

- 已有 2 條執行中的通道時不成立：第一個成功後就滿 3 條，第二個回 409 `max_devices_reached`。第二個請求的呼叫端拿到「已連接最多 3 台裝置」，但那支手機其實已經由第一個請求連上。
- 01 號票實作時發現、沒修（`:361-364`）：
  - 原因：`wifi_tunnel_start` 開頭的上限檢查排在 `already_running` 判斷前面。
  - 改之前也一樣：已有 3 條通道時，對其中一條的 IP 再送一次會回 409。01 號票「判斷照舊」，所以維持這個順序。
  - 自動連線和 WiFi 掃描走不到這條：前端會跳過通道手機的 IP（`frontend/src/wifiCandidates.ts:112`）。
- 會把同一個 IP 送兩次的來源，01 號票「不做」列過（`:183`）：
  - 釘選裝置斷線後每 15 秒的重試。
  - 重新整理頁面時，上一個請求還在跑。
  - 開了兩個分頁。

下面的行號都是 `5641f5c` 時的位置。動手前以內容為準，先用 grep 再對一次。

## 現況

- `backend/api/device.py` 的 `wifi_tunnel_start`，開頭那段在 `:999-1039`：
  - `:1005`：上限檢查，`_tunnel_slots_in_use() >= MAX_DEVICES` 就回 409。
  - `:1018-1031`：同一個 (IP, Port) 已有執行中的通道，就回 `already_running`。
  - `:1039`：同一個 IP 在握手時，`await earlier.wait()` 等它結束，醒來從 `:1000` 重來，先碰到 `:1005`。
- 開票時另外發現，01 號票沒寫：前端走的是 `start-and-connect`，它在呼叫 `wifi_tunnel_start` 之前，還有一次上限預檢（`:1403-1408`）。01 號票把這次預檢改成同一個計數（`:228`）。
  - 第一個請求登記握手中之後，名額算成 3 個：2 條通道加 1 個握手中。
  - 第二個請求在預檢就回 409，不會進到 `wifi_tunnel_start` 去等第一個。
  - 所以只對調 `wifi_tunnel_start` 裡的兩個判斷不夠，預檢也要處理。
- 用假的 `TunnelRunner` 和假的 device manager 跑過，寫法同 `tests/device/test_wifi_tunnel_parallel_start.py`，腳本沒進 repo。同一個 IP 同時送兩次，握手 0.3 秒：

| 已有通道 | 直接呼叫 `wifi_tunnel_start` | 呼叫 `start-and-connect` |
|---|---|---|
| 1 條 | `started`、`already_running`，都是 0.31 秒 | 兩個都 `connected`，0.42 秒 |
| 2 條 | `started`、409，409 在 0.31 秒回（等完第一個才回） | `connected`、409，409 在 0 秒回（預檢就回了） |

- 「1 條、`start-and-connect`」那格，兩個請求都對同一支手機 `connect_wifi_tunnel`，是 04 號票的情況。

## 可能的做法

- A. 不修，改成 `wontfix`：
  - 自動連線和 WiFi 掃描走不到。
  - 碰到的時候，第一個請求已經連上，第二個只是多拿到一個錯誤。
  - 行為跟 01 號票改之前一樣。
- B. 把 `already_running` 判斷挪到上限檢查前面：
  - `wifi_tunnel_start`：同一個 (IP, Port) 已有執行中的通道，就先回 `already_running`，不看上限。
  - `start-and-connect` 的預檢也要讓這種請求通過，不然 409 在預檢就回了。預檢跟 `wifi_tunnel_start` 自己的上限檢查看起來重複，可以考慮拿掉，triage 時確認。
  - 副作用（2026-11-09 triage 更正）：已有 3 條時對其中一條再送一次，只有直接呼叫 `wifi_tunnel_start` 會從 409 變成 `already_running`。
    - 前端走的 `start-and-connect` 不會：`wifi_tunnel_start` 回 `already_running` 之後，連線前的裝置數檢查（`:1438`）看到 3 台，不帶 `skip_connected` 還是回 409。
  - 只做上面兩步不夠，已有 2 條時也達不到目的，見 Comments 2026-11-09 triage 那則。

## 待 triage 決定

- 選 A 或 B。
- 選 B 的話：
  - 預檢要改條件，還是拿掉。
  - 測試：
    - `test_wifi_tunnel_parallel_start.py` 第 3 條（已有 2 條，同時送 2 個不同 IP，一個 409）要照樣通過。
    - 新增「已有 2 條，同一個 IP 送兩次」的測試，`wifi_tunnel_start` 和 `start-and-connect` 兩條路都要測。
    - 「已有 3 條，對其中一條再送一次」的新預期也要鎖住。
