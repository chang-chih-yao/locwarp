# 03 裝置連線：`start-and-connect` 檢查裝置上限和連線之間沒有鎖，1 台 USB 加 3 個 WiFi 請求可能連上 4 台

## 為什麼

裝置上限是 3 台（`MAX_DEVICES`，`backend/api/device.py:87`）。`start-and-connect` 有兩道上限檢查，只有第一道在鎖裡：

- 開頭的預檢（`:1403-1408`）算的是 WiFi 通道的名額：執行中的通道加握手中的請求（`_tunnel_slots_in_use()`，`:103-109`），不算 USB 裝置。這是 01 號票改的，在 `_tunnels_lock` 裡。
- 通道建好後、`connect_wifi_tunnel` 之前，用 `len(dm._connections)` 檢查裝置數（`:1438-1442`）。這道有算 USB 裝置，但沒有鎖。
  - 檢查完到 `connect_wifi_tunnel` 寫入 `_connections`（`backend/core/device_manager.py:631-632`）之間，隔著 RSD 連線，最多重試 10 次（`:564`）。
- 所以 1 台 USB 已連上時，同時送 3 個不同 IP：
  - 通道名額 3 個，都過。
  - 3 個請求在 `:1438` 都看到 1 台，都過。
  - 最後連上 4 台。
- 01 號票記下的（`:365-368`）：
  - 改之前也有這個空檔，只是握手一個接一個，比較難碰到。
  - 前端 `fillFreeSlots` 同時送出的數量不超過「3 − 已連上台數」，自動連線和 WiFi 掃描碰不到。要碰到，得手動連線跟 WiFi 掃描同時進行。
  - 要不要在掃描時停用手動連線的按鈕，是 05 號票。

下面的行號都是 `5641f5c` 時的位置。動手前以內容為準，先用 grep 再對一次。

- A. 不修，改成 `wontfix`：前端的正常流程碰不到。
