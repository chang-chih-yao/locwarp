# 04 裝置連線：同一支手機可能同時被兩個 `start-and-connect` 連線

Status: needs-info
Blocked by: (none)
Type: bug
相關：`.scratch/wifi-tunnel-parallel-start/issues/01-parallel-tunnel-start.md` 的「不做」（`:179-181`）、「已決定」第 4 點（`:195`）、brief 的「不做」（`:312`）。

## 為什麼

這是 01 號票 triage 時補的（`:179-181`），決定只記下、不修（`:195`）：

- 情況：同一個 IP 送兩次，或同一支手機有兩個 IP 時，第二個請求拿到 `already_running` 之後，可能跟第一個請求同時對同一個 UDID `connect_wifi_tunnel`。
- `connect_wifi_tunnel` 遇到已連上的 UDID，會先斷線。兩邊可能互相斷掉，各自重建模擬引擎。
- 現在就會發生：`_tunnels_lock` 在 `connect_wifi_tunnel` 之前就放掉了。01 號票的改動不會讓它變糟。

01 號票確認過的是兩台不同的手機同時連（`:352-356`），不是這張說的同一台。

下面的行號都是 `5641f5c` 時的位置。動手前以內容為準，先用 grep 再對一次。

## 現況

- `start-and-connect`，`backend/api/device.py:1391` 起：
  - `wifi_tunnel_start` 回 `started` 或 `already_running`，都往下走（`:1411`）。
  - `skip_connected`（自動連線和 WiFi 掃描都會帶）只在 `:1430` 看一次這個 UDID 在不在 `dm._connections`。
    - 兩個請求差不多同時到這裡時，第一個的 `connect_wifi_tunnel` 還沒寫入 `_connections`（`backend/core/device_manager.py:631-632`），所以第二個也會過。
    - 寫入前面是 RSD 連線，最多重試 10 次（`:564`）。
  - 接著兩個請求都呼叫 `connect_wifi_tunnel`（`:1444`），再各自拿掉模擬引擎、重建一個（`:1455-1456`）。
- `connect_wifi_tunnel` 在 `device_manager.py:619-620` 遇到已連上的 UDID，先 `disconnect`。`disconnect`（`:335` 起）會清掉定位、關 DVT、關 RSD。
- 用假的 `TunnelRunner` 和假的 device manager 跑過，寫法同 `tests/device/test_wifi_tunnel_parallel_start.py`，腳本沒進 repo：
  - 一支手機兩個 IP 同時送，帶 `skip_connected`：兩個都回 `connected`，`connect_wifi_tunnel` 被呼叫兩次，都是同一個 UDID。
  - 已有 1 條通道，同一個 IP 送兩次，不帶 `skip_connected`：兩個也都回 `connected`（02 號票的表）。
- 換成真的 `DeviceManager` 會怎樣，沒有驗證：
  - 哪一個連線被斷掉。
  - 最後留下的模擬引擎，綁的是哪一個連線。
  - 正在跑的路線會不會被中斷。
- 會碰到的來源：
  - 同一個 IP 送兩次：01 號票 `:183` 列的那幾個（釘選重試、重新整理頁面、兩個分頁）。
  - 同一支手機有兩個 IP：01 號票沒寫什麼時候會有，開票時也沒查。
    - 前端同一次掃描裡，一個 UDID 只出一個候選（`frontend/src/wifiCandidates.ts:125-134`）。

## 可能的做法

- A. 不修，改成 `wontfix`：維持 01 號票的決定。
- B. 在 `start-and-connect` 擋：
  - 同一個 UDID 已有請求在連線時，第二個請求等它結束，再看 UDID 是不是已經在 `dm._connections`。
  - 需要一個「這個 UDID 連線中」的登記，類似 01 號票的 `_tunnel_starts_in_flight`（`backend/api/device.py:100`）。
  - 不帶 `skip_connected` 的請求（手動連線、釘選重試）等完之後要怎麼做，要另外決定：直接回已連上，或照現在的做法重連。
- C. 在 `DeviceManager.connect_wifi_tunnel` 裡，對同一個 UDID 一次只讓一個連線進行。
  - UDID 要等 RSD 連上之後才知道（`device_manager.py:591`），所以只能擋住後半段，RSD 連線那段還是會重複做。
