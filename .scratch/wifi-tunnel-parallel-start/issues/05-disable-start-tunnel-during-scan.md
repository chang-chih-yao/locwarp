# 05 裝置連線：WiFi 掃描或自動連線進行中，要不要停用 WiFi 面板的「Start WiFi Tunnel」

## 為什麼

這是 01 號票 triage 時使用者問起的（`:182-184`），當時列為不做：

- 同一個 IP 同時送兩次，還有其他來源：釘選裝置斷線後每 15 秒的重試、重新整理頁面時上一個請求還在跑、開了兩個分頁。停用按鈕擋不完，後端反正要處理。
- 要不要停用，是介面上的另一個選擇，需要時另開票。這張就是那張。

下面的行號都是 `5641f5c` 時的位置。動手前以內容為準，先用 grep 再對一次。

## 現況

- 「Start WiFi Tunnel」在 `frontend/src/components/DeviceStatus.tsx`，`:1047` 的 `disabled` 只看 `tunnelConnecting || portScanning`，也就是它自己的連線和掃 Port。
- WiFi 掃描的按鈕已經會在自動連線時停用（`:188`）：
  - `wifiScanDisabled = !onWifiScan || wifiScanning || autoConnectRunning || wifiFull`。
  - 註解寫的理由是「so the two never handshake one phone at once」。
  - 反過來，手動連線進行中時，WiFi 掃描的按鈕不會停用：`wifiScanDisabled` 沒看 `tunnelConnecting`。
- 這兩個狀態都在同一個元件裡：`wifiScanning` 是本地 state（`:183`），`autoConnectRunning` 是 prop（`:45`、`:68`）。
- 手動連線跟 WiFi 掃描同時進行時，碰得到的後端問題：
  - 03 號票：1 台 USB 加 3 個同時送的 WiFi 請求，可能連上 4 台。前端只有這條路碰得到（另一條插 USB 的是讀程式碼推的）。
    - 2026-11-09：03 號票 triage 用假的 runner 模擬過插 USB 那條，有 4 支不同的 iPhone 就碰得到，03 號票已改成 `wontfix`，見那張的 triage Comment。
  - 02、04 號票：同一個 IP 送兩次。前提是手動輸入的 IP 剛好是這次掃描的候選。

## 可能的做法

- A. 不停用，改成 `wontfix`：01 號票的理由還在，按鈕擋不完，該在後端處理（02～04 號票）。
  - 2026-11-09：02、03 號票 triage 為 `wontfix`，不修在後端；04 號票改成 `needs-info`，等真手機查證。見 Comments 2026-11-09 triage 那則。
- B. 停用：`disabled` 加上 `wifiScanning || autoConnectRunning`，比照 WiFi 掃描按鈕在自動連線時停用的做法。
  - 要不要連同一塊的其他控制項一起停用。它們現在也只看手動連線自己的狀態：
    - IP 欄位（`:900`）和「最近的 IP」按鈕（`:906`）：`tunnelConnecting`。
    - Port 欄位（`:968`）和掃 Port 按鈕（`:974`）：`tunnelConnecting || portScanning`。
  - 要不要反過來：手動連線進行中時，WiFi 掃描的按鈕也停用。
  - 停用時要不要顯示原因。
